Lambda 셋, GPU 워커 풀, Bedrock

사진 분석은 wes-app이 단계마다 EVENT로 부르는 Lambda 셋(embedder → score → categorize)과, score 단계를 대신 처리하는 GPU 워커 두 대가 맡습니다. Lambda는 인터넷 경로가 없는 DB 서브넷에서 실행되며 S3 게이트웨이·bedrock-runtime 엔드포인트만으로 바깥과 통신합니다. Lambda끼리는 서로 부르지 않고, 다음 단계는 wes-app이 DB를 보고 결정합니다.

아키텍처

실선은 호출·쓰기, 점선은 읽기·관측입니다. 박스를 누르면 해당 절로 이동합니다.

Lambda 세 개는 같은 SG(wes-embedder-*)를 공유하고, RDS SG는 그 SG와 GPU SG를 각각 인바운드로 허용합니다. Lambda가 S3를 읽는 길은 DB 라우트 테이블에 붙은 게이트웨이 엔드포인트(무료)이고, public subnet의 GPU 워커는 IGW로 S3에 갑니다. categorize가 Bedrock을 부르는 길은 2a 한 곳의 인터페이스 엔드포인트입니다.

Lambda 셋

세 함수 모두 컨테이너 이미지(x86_64, ECR :latest) · 타임아웃 900초 · DB 서브넷 두 곳 · 로그 보존 14일입니다. 이름은 wes-{embedder,score,categorize}이고 함수 이름은 SSM에 써서 wes-app이 부팅 때 읽습니다. 코드는 AI repo 최상위 디렉토리 하나 = 함수 하나입니다.

비동기 호출 · 알람

  • 재시도 0회, 이벤트 최대 보관 1200초(20분). wes가 EVENT로 던지고 응답을 기다리지 않으므로, Lambda가 실패하면 같은 사진이 다음 스윕에서 다시 배정되는 쪽에 맡깁니다.
  • 함수마다 알람 둘 — <fn>-async-event-age(AsyncEventAge 최대 ≥ 10분, 2/2 데이터포인트)과 <fn>-async-events-dropped(Dropped 합 > 0). 알람 액션은 없고 콘솔에서 확인합니다. 에러 수 알람은 없습니다.

ECR

저장소 셋(wes-embedder · wes-score · wes-categorize) 모두 scan_on_push, force_delete. 라이프사이클은 태그 없는 이미지 3일 뒤 만료이고, score만 gpu-<sha> 태그를 최근 3개까지 보존합니다. 이동 태그 gpu·latest는 규칙에 걸리지 않습니다. 푸시 주체는 AI repo의 GitHub Actions(worker 롤)이며, Lambda는 UpdateFunctionCode로 갱신되고 GPU 워커는 부팅 때 wes-score:gpu를 pull합니다.

AMIgpu_ami_id 고정 핀(기본 ami-0f2e11582fb0a76da) · most_recent 안 씀
디스크gp3 30GB 암호화 · 처리량 125MB/s

초기 상태생성 직후 stopped (aws_ec2_instance_state, state ignore)
태그Name=wes-score-gpu · Role=score-gpu-worker

user_data가 없습니다. systemd 유닛과 스크립트는 AMI에 구워져 있고, 인스턴스가 켜지면 wes-score.service가 순서대로 (1) SSM에서 값 3개를 읽어 /run/wes-score.env를 쓰고 (2) ECR 로그인 뒤 wes-score:gpu를 pull하고 (3) docker run --gpus all로 워커를 띄웁니다. 워커는 DB에서 32장씩 직접 집어 점수를 내고, 30초 동안 집을 것이 없으면 자기 인스턴스를 정지합니다.

ExecStart=/usr/bin/docker run --rm --name wes-score --gpus all --env-file /run/wes-score.env \
  -e DB_USER=photoselect -e DB_SSLMODE=verify-full -e DB_SSLROOTCERT=/opt/rds-ca/global-bundle.pem \
  -e WORKER_IDLE_STOP_SECONDS=30 <ECR>/wes-score:gpu
# Restart=on-failure · RestartSec=15 · StartLimitBurst=3/600s · OnFailure=wes-score-failsafe.service(자기 정지)

켜고 끄는 주체 네 겹

  1. wes-app이 켠다. score 대기 사진이 있으면 StartInstances(태그 조건). ScoreWorkerSupervisor.
  2. 워커가 스스로 끈다. WORKER_IDLE_STOP_SECONDS=30 — 집을 사진이 30초 없으면 IMDSv2로 자기 ID를 얻어 stop-instances. 1차 정지 경로.
  3. wes-app 안전망. backlog 0 뒤 2분 무진행이면 StopInstances. 10분 무진행이면 score Lambda 폴백.
  4. CloudWatch 알람. wes-score-gpu-idle-stop-<az> — CPU 평균 < 5%, 300초 × 6 = 30분 연속 → arn:aws:automate:…:ec2:stop. 최후 수단.
gpu_score_enabled 플래그
Terraform 변수 gpu_score_enabled(기본 true, 2026-09-08부터)는 SSM /wes/prod/app.analysis.gpu.enabled 문자열만 바꿉니다. GPU 인프라를 만들거나 지우지 않으며, wes-app이 부팅 때 읽으므로 앱 재시작이 필요합니다. 인스턴스가 0대여도 정상 상태이고 wes는 score Lambda로 폴백합니다. 정지된 인스턴스는 공인 IP를 잃어 매 plan마다 replace되던 문제가 있어 associate_public_ip_address를 ignore_changes로 두었습니다(#57).

AMI 파이프라인 (EC2 Image Builder)

  • 수동 실행만. 파이프라인에 schedule이 없습니다. aws imagebuilder start-image-pipeline-execution → g6.xlarge에서 빌드(재부팅 2회) + 테스트 인스턴스, 25~35분. 나온 AMI(Name=wes-score-gpu-ami)를 gpu_ami_id에 핀해 PR → 워커 2대 replace.
  • 레시피 wes-score-gpu 1.0.2: 부모 이미지 AL2023 x86 최신, 루트 gp3 30GB, SSM 에이전트 유지. 컴포넌트 wes-score-gpu-nvidia-docker 1.0.2: OS 업데이트 → NVIDIA 드라이버 580 브랜치(versionlock, 최소 major 525 검증) → Docker + nvidia-container-toolkit → /etc/wes-score/image.env와 스크립트 3개·유닛 2개 설치 → wes-score.service enable. 드라이버·유닛을 바꾸면 두 버전을 올려야 apply가 통과합니다.
  • 서비스 연결 역할 둘(AWSServiceRoleForImageBuilder, AWSServiceRoleForCloudWatchEvents)을 코드로 만들며, tf_apply 롤은 이 둘만 만들 수 있습니다. G 인스턴스 쿼터는 8 → 12 vCPU로 올려 두었습니다.

Bedrock

categorize가 그룹 이름을 지을 때 global.anthropic.claude-sonnet-4-6 추론 프로필을 InvokeModel로 부릅니다. DB 서브넷에는 인터넷 경로가 없으므로 bedrock-runtime 인터페이스 엔드포인트를 2a 한 곳에만 두었고(interface_endpoint_subnet_indexes=[0], 약 $11/월), 한때 있던 lambda 인터페이스 엔드포인트는 Lambda 간 호출을 없애며 함께 제거했습니다(#57). wes-app의 추천 LLM 호출은 public subnet에서 IGW로 나가며 앱 롤에 별도 InvokeModel 권한이 있습니다.
