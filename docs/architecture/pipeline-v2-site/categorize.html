아키텍처

실선은 호출·저장, 점선은 조회·상태 확인입니다. 박스를 누르면 해당 단계의 설명으로 이동합니다.

ANALYZING→ livePending 0 ∧ scored == expected → CATEGORIZING→ 배정 행 ∧ categorized == expected → 물질화 → DONE │ error / 3회 타임아웃 / 사진 0장 →FAILED

① 잡 생성 — POST /ai-analysis

한다"이 갤러리 폴더 만들어 달라"를 ai_analysis_jobs 행(ANALYZING) 하나로 만든다. 게이트는 uploader 권한, 실행기 설정, 업로드된 사진 ≥1, 활성 잡 없음. 커밋 뒤 즉시 한 걸음 돌린다.왜임베딩·점수는 잡 없이도 돌지만 그룹·이름·폴더는 갤러리 단위로 "한 번" 해야 하고, 그 한 번을 누가 언제 시작했는지가 필요하다. 갤러리당 활성 잡 하나(부분 유니크)라야 categorize 가 두 번 돌지 않는다. 본문이 없는 이유는 mode·force 를 없앤 v2 결정이다.없으면같은 갤러리에 잡이 둘 생겨 폴더 세트가 둘 만들어지거나, 사진이 하나도 없는 갤러리에 빈 잡이 굳는다.입출력POST /ai-analysis → 202 {jobId, status, progress} · 409 RECOMMENDATION_409_1/2
  1. 인가 requireUploader.
  2. 실행기 설정 확인 — Embed·Categorize 함수 이름, 그리고 gpu.enabled=false 일 때만 Score 도 필수. 비면 503 PHOTO_503_1 STAGE_NOT_CONFIGURED.
  3. 진행 카운트 progressOf(gallery, liveSince = now − 2분). expected == 0 → 409 RECOMMENDATION_409_2 NO_PHOTOS_TO_ANALYZE.
  4. 활성 잡 검사 existsByGalleryIdAndStatusIn(ACTIVE) → 409 RECOMMENDATION_409_1. 부분 유니크 uk_ai_analysis_jobs_active 충돌도 같은 코드.
  5. INSERT AnalysisJob(galleryId) 상태 기본 ANALYZING → saveAndFlush.
  6. afterCommit orchestrator.dispatch(jobId) = 즉시 stepJob 한 번(점수가 이미 다 있으면 바로 CATEGORIZING). 응답 202 + {jobId, galleryId, status, progress{expected, embedded, scored, categorized, failed}, error, createdAt, finishedAt}.

409_1 을 받은 프론트는 GET /ai-analysis 를 한 번 읽고, 잡이 CATEGORIZING 이면 "끝나면 이어서" 예약, ANALYZING 이면 그 잡이 새 사진을 흡수한다고 보고 넘어간다.

트랜잭션 밖에서 실행할 작업 하나
OrchestratorActionDto는 잡의 상태를 확인한 뒤 수행할 작업을 담습니다. Invoke(jobId, call)의 call은 StageCallDto.Categorize 한 건입니다. 임베딩 배정과 score 폴백은 스윕에서 각각 실행되며 이 액션에 포함되지 않습니다. 폴더 생성은 Materialize(jobId, galleryId)로 전달합니다.

② stepAnalyzing — 관측만 한다

한다매 걸음 카운트를 다시 세어 livePending == 0 ∧ scored == expected 면 CAS 로 CATEGORIZING 에 들어가며 categorize 를 딱 한 번 보낸다. 사진이 0장이면 FAILED.왜"점수가 다 찼다"는 사실은 DB 에만 있으므로 잡이 관측해야 한다. 업로드 도중 뒤늦게 온 사진(2분 창)을 흡수하려면 expected 를 매번 다시 세야 하고, 스윕 둘이 같은 잡을 밟아도 EVENT 가 한 번만 나가야 하므로 version 조건의 CAS 로 전이한다.없으면점수가 덜 찬 채 분류가 시작돼 일부 사진이 "기타"로 가거나, 두 스윕이 categorize 를 두 번 불러 Bedrock 비용이 두 배가 된다.
progress = progressOf(galleryId, liveSince = now − uploadQuietAfter(2m))
if livePending == 0 ∧ pending == 0 ∧ expected == 0:
    job.fail("분석할 사진이 없습니다(실패 N장)")            # ANALYZING→FAILED
elif livePending == 0 ∧ expected > 0 ∧ scored == expected:
    job.startCategorizing(now)                          # CATEGORIZING, dispatched_at=now, attempts=1
    log  analysis job=J gallery=G ANALYZING->CATEGORIZING expected= embedded= scored= failed= elapsed=…s
    return OrchestratorActionDto.Invoke(jobId, StageCallDto.Categorize(galleryId, jobId))   # 트랜잭션 커밋 뒤 EVENT
else: return null                                       # 다음 스윕
  • 흡수 규칙. expected(UPLOADED ∧ error 없음)를 매 걸음 다시 세고, 최근 2분 안에 발급된 PENDING(livePending)이 있으면 넘어가지 않는다. 업로드 중간에 잡을 만들어도 뒤늦게 올라온 사진이 같은 잡에 들어간다.
  • CAS. 걸음은 REQUIRES_NEW 트랜잭션 하나이고 AnalysisJob.version(낙관적 잠금)이 조건이다. 스윕 둘이 같은 잡을 밟으면 진 쪽은 ObjectOptimisticLockingFailureException 으로 걸음을 버리고 EVENT 를 보내지 않는다.
  • 호출 실패. Lambda 호출이 예외면 job.dispatchFailed() 로 dispatched_at 을 지워 다음 스윕이 즉시 재전송. 잡은 닫지 않는다.

③ stepCategorizing — 결과 관측 · 타임아웃

한다categorize 결과를 관측한다: 배정 행이 있고 백분위가 다 찼으면 물질화로, error 가 있으면 FAILED, 20분 무응답이면 3회까지 재전송.왜Lambda 는 잡 상태를 쓰지 않는다(실패 시 error 만). 그래서 "끝났다"를 배정 행 존재와 technical_pct 카운트로 읽고, "죽었다"를 타임아웃으로 판단해야 한다. categorize 가 UPSERT 라 재전송이 겹쳐도 안전하다.없으면Lambda 가 조용히 죽으면 잡이 CATEGORIZING 으로 굳고, 배정만 보고 넘어가면 백분위가 비어 추천이 틀린다.
if job.error != null:                      job.fail(error)                    # Lambda 가 남긴 실패 → FAILED
elif existsAssignments(jobId) ∧ categorized == expected:
    return OrchestratorActionDto.Materialize(jobId, galleryId)                              # → 6. 폴더 물질화 → DONE
elif dispatched_at + 20m > now:            return null                       # 아직 기다림
elif attempts ≥ 3:                         job.fail("categorize 를 3회 시도했지만 끝나지 않았습니다")
else: job.redispatchCategorize(now); return OrchestratorActionDto.Invoke(jobId, StageCallDto.Categorize(galleryId, jobId))        # attempts+1, 재전송

categorized 는 technical_pct IS NOT NULL 카운트 — categorize 가 갤러리 전체를 다시 계산해 write_groups 하면 채워진다. 배정 행 존재(ai_concept_assignments.job_id)는 naming 까지 끝났다는 뜻. 둘 다 맞아야 물질화한다. categorize 는 재실행 안전(UPSERT)이라 재전송이 겹쳐도 괜찮다.

④ 물질화 → DONE

한다배정 행이 폴더가 되게 물질화를 자기 트랜잭션으로 부르고, 결과(Created / NothingNew / Failed)로 잡을 닫으며 Created 면 알림 1건을 같은 트랜잭션에서 보낸다.왜사용자 관점의 완료는 "폴더가 생겼다"이지 "배정 행이 생겼다"가 아니다. 물질화가 수 초~수십 초라 걸음 트랜잭션과 분리하고, 잡 닫기와 알림을 한 트랜잭션에 묶어 알림이 두 번 가거나 안 가는 일을 막는다.없으면폴더는 사용자가 버튼을 눌러야 생기고(v1), 알림이 잡과 어긋나 중복 발송된다.

OrchestratorActionDto.Materialize 는 걸음 트랜잭션이 끝난 뒤 AiCategoryFolderService.materializeFromAnalysis(galleryId) 를 자기 트랜잭션으로 부른다(갤러리 락, 수 초~수십 초). 그 결과로 또 다른 트랜잭션에서 잡을 닫는다.
