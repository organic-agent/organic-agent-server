임베딩할 사진 배정

wes는 5초마다 업로드가 끝난 사진 중 벡터가 아직 없는 사진을 50장씩 선택해 embedder Lambda에 전달합니다. DB 잠금으로 중복 배정을 막으며, 분석 잡 생성 여부와 관계없이 동작합니다.

아키텍처

실선은 호출·저장, 점선은 조회·상태 확인입니다. 박스를 누르면 해당 단계의 설명으로 이동합니다.

언제 · 무엇을 배정하나

한다5초마다 UPLOADED 인데 벡터가 없는 사진을 갤러리별로 50장씩 SKIP LOCKED 로 집어 embedder Lambda 를 EVENT 로 부른다. 잡과 무관하게 돈다. 10분 넘게 벡터가 안 오면 되돌리고, 3회 넘으면 error 로 표시한다.왜임베딩은 사진이 올라오는 족족 시작돼야 업로드가 끝났을 때 이미 절반이 돼 있다. Lambda 는 사진 50장 단위(사진당 호출 없음)로 불러야 콜드스타트·비용이 맞고, 전역 32배치 상한은 Lambda 예약 동시성과 RDS 커넥션을 지키기 위해서다. 갤러리 라운드로빈은 큰 갤러리 하나가 슬롯을 독점하지 않게 한다.없으면"분석 시작" 버튼을 눌러야 임베딩이 시작돼 업로드 시간 + 분석 시간이 합쳐지고, 배정이 없으면 두 스윕이 같은 사진을 두 번 보내거나 죽은 Lambda 의 사진이 영영 남는다.입출력photos(UPLOADED ∧ embedding NULL) → StageCall.Embed(galleryId, photoIds[≤50])

트리거는 잡이 아니라 데이터다. POST /ai-analysis 를 눌렀는지와 무관하게, 스윕은 매 5초 아래 조건의 사진을 찾는다.

status = 'UPLOADED' AND deleted_at IS NULL
AND dispatched_at IS NULL AND embed_attempts < 3
AND a.embedding IS NULL AND a.error IS NULL        -- a = LEFT JOIN photo_analysis
  1. 가용성 확인. stageInvoker.isAvailable(Embed) 가 false(함수 이름 미설정 / 로컬 스크립트 없음)면 아무것도 안 한다.
  2. stale 배정 되돌림. dispatched_at < now − 10분 인데 아직 embedding 도 error 도 없는 사진은 dispatched_at = NULL 로 되돌린다(시도 수는 유지). Lambda 가 죽었거나 남은 장(remaining)을 못 처리한 경우다.
  3. 상한 초과 표시. dispatched_at IS NULL ∧ embed_attempts ≥ 3 ∧ 벡터·error 없음 인 사진에 photo_analysis 행을 UPSERT 해 error = 'EMBED_ATTEMPTS_EXCEEDED'. 이후 배정·집기·기대 장수에서 빠지고 /photos/summary.failed 로 드러난다.
  4. 빈 슬롯 계산. slots = 32 − countInFlightEmbedBatches(). in-flight 는 배치 수다 — 한 배치의 50장이 같은 statement_timestamp() 를 공유하므로 count(DISTINCT dispatched_at) 로 센다. 최대 32배치 = 1,600장이 동시에 Lambda 에 나가 있다.
  5. 갤러리 라운드로빈. backlog 있는 갤러리를 min(photo_id) 순으로 돌며 갤러리마다 한 배치(50장)씩 집는다. 슬롯이 남으면 다시 한 바퀴, 한 바퀴에 0건이면 끝. 큰 갤러리 하나가 슬롯을 독점하지 않는다.
  6. 집기. claimForEmbedding — 조건에 맞는 50장을 FOR UPDATE OF p SKIP LOCKED 로 잠그고 dispatched_at = statement_timestamp(), embed_attempts += 1 로 갱신하며 RETURNING id. 스윕 둘이 겹쳐도 같은 사진을 두 번 집지 않는다.
  7. 호출. StageCallDto.Embed(galleryId, photoIds) → EVENT. 호출 자체가 실패(AnalysisException)하면 releaseClaim 이 dispatched_at = NULL, embed_attempts −1 로 되돌리고 이번 걸음을 중단한다. 성공 로그 embed dispatch gallery=G photos=N.

호출 계약

한다실행기(Lambda / 로컬 스크립트)를 StageInvoker 포트 뒤에 숨긴다. prod 는 InvocationType.EVENT 로 세 함수를 부르고, local 은 같은 인자로 scripts/lambda/*.sh 를 띄운다.왜wes 는 응답을 기다리지 않고 DB 를 관측하는 구조라 호출은 "던지고 잊기"면 충분하다. 포트로 분리하면 로컬 개발이 Lambda 없이 같은 흐름을 돌리고, 테스트는 호출 기록만 확인한다. 페이로드 모양이 세 함수 모두 단순한 것({galleryId, photoIds} / {galleryId, jobId})도 체인·샤딩을 없앤 결과다.없으면로컬에서 파이프라인을 돌릴 수 없고, 동기 호출이면 wes 스레드가 Lambda 15분을 기다린다.입출력StageCall → EVENT 202 (실패 STAGE_INVOCATION_FAILED)
환경어댑터무엇을 부르나
prod (!local)LambdaStageInvokerInvocationType.EVENT, 함수 이름 app.analysis.embedder-function-name(SSM). 페이로드 {"galleryId":G,"photoIds":[…]}. 202 아니면 STAGE_INVOCATION_FAILED(502 PHOTO_502_1)
localLocalProcessStageInvokerscripts/lambda/embedder.sh --gallery-id G --photo-ids 1,2,3 을 ProcessBuilder 로 띄우고 기다리지 않음. 로그 ${java.io.tmpdir}/wes-lambda-embedder-G.log

일반 분석의 Score 폴백도 같은 모양 {galleryId, photoIds}, Categorize 만 {galleryId, jobId}. 세 함수 모두 wes가 응답을 기다리지 않고(EVENT) DB를 관측한다. 운영 어댑터는 ObjectMapper.writeValueAsBytes(call)로 DTO를 직렬화하며, 프로퍼티 이름이 그대로 JSON 키가 된다. 일반 Embed 요청에는 jobId를 넣지 않는다. 임베더 응답 {processed, failed, metadataFailed, stopped, remaining} 은 CloudWatch 에만 남고, 남은 장은 2단계의 stale 되돌림이 재배정한다.

관리자 사진 교체도 같은 실행 포트를 사용

관리자가 사진을 교체하면 AdminWorkflowExecutor가 교체된 리비전의 사진 1장을 StageCallDto.ExactPhoto로 요청합니다. 일반 배치와 같은 StageInvoker·LambdaStageInvoker를 사용하지만, embedder는 jobId가 있는 요청을 관리자 사진 교체 이벤트로 해석합니다.

운영과 로컬의 차이
운영은 embedder-function-name을 일반 Embed와 공유합니다. 문자열 필드도 ObjectMapper가 JSON으로 안전하게 직렬화합니다. 로컬의 isAvailable(ExactPhoto::class)는 false이므로 관리자 잡은 전송 전에 PHOTO_PROCESSING_NOT_CONFIGURED로 실패 처리됩니다. 직접 invoke(ExactPhoto)하면 STAGE_INVOCATION_FAILED가 발생하며 스크립트는 실행되지 않습니다.

외부 호출 중 예외가 나면 수락 여부를 확정할 수 없으므로 관리자 경로는 결과 불명 상태로 기록합니다. 일반 분석 잡의 자동 재전송과는 복구 정책이 다릅니다. 갤러리 전체 재분석은 계속 resetAnalysis 후 스윕 재배정을 사용합니다.

잡과의 관계

한다잡 걸음은 배정에 관여하지 않고 카운트만 관측한다. livePending == 0 ∧ scored == expected 가 되면 CATEGORIZING 으로 넘어간다.왜임베딩·점수는 데이터가 트리거이고 잡은 "갤러리 한 번의 폴더 만들기"만 책임진다. 이렇게 갈라야 잡이 없어도 사진은 끝까지 분석되고, 잡은 업로드 도중 뒤늦게 온 사진(2분 창)을 흡수한다.없으면잡이 배정까지 맡으면 잡이 죽을 때 파이프라인이 서고, 업로드 중간에 만든 잡은 늦게 온 사진을 놓친다.

스윕의 잡 걸음(stepAnalyzing)은 배정을 하지 않고 관측만 한다. livePending == 0 ∧ scored == expected 가 되면 CATEGORIZING 으로 넘어간다(5. 사진 분류). livePending 은 최근 2분(upload-quiet-after) 안에 발급된 PENDING 이라, 업로드 도중에 잡을 만들어도 뒤늦게 올라오는 사진을 흡수한다. 살아 있는 잡이 없어도 임베딩·점수는 끝까지 진행되고, 폴더만 다음 방문의 버튼 한 번으로 만들어진다.

재분석
관리자 재처리(AdminReprocessService)는 Lambda 를 직접 부르지 않는다. resetAnalysis(galleryId) 로 photo_analysis 행을 지우고 dispatched_at=NULL, embed_attempts=0 으로 되돌린 뒤 활성 잡이 없으면 잡을 만든다. 다음 스윕이 처음부터 다시 배정한다.
