사진은 브라우저에서 S3로 직접 업로드됩니다. wes는 5초마다 DB의 진행 상태를 확인하며 임베딩·점수 계산·분류를 조율하고, 분석이 끝나면 사진을 폴더로 정리합니다.

서비스 아키텍처

엔티티 필드 사전 ↗

영역의 번호 순서로 읽으세요. 실선은 호출·저장, 점선은 조회·상태 확인입니다. 실행기 사이의 다음 단계는 wes가 DB를 확인해 결정합니다.

미리보기는 S3에, 분석 결과는 DB에 저장됩니다. 브라우저는 wes API로 진행 상황을 조회하고, 완료되면 폴더를 다시 불러옵니다.

컴포넌트별 상세 연결도 클래스명 · 호출 인자 · 재시도 경로

서버 실행 경계와 호출 계약

서버의 외부 실행은 analysis/service/port의 두 포트를 통과합니다. StageInvoker는 Lambda 호출을, ScoreWorkerPool은 GPU 워커의 시작·정지와 상태 조회를 담당합니다. 호출 데이터는 analysis/dto/StageCallDto의 네 가지 타입으로 구분합니다.

운영은 LambdaStageInvoker가 DTO를 JSON으로 직렬화해 EVENT로 호출합니다. 로컬은 LocalProcessStageInvoker가 스크립트를 실행하며, 관리자 사진 교체(ExactPhoto)는 지원하지 않습니다.

파이프라인의 기본 원칙

  • 이미지 바이트는 서버를 지나지 않는다. 브라우저 ↔ S3 직접. 서버가 AI 호출용 미리보기 몇 장을 읽는 것은 무방하다.
  • 체인·샤딩·자기 재호출은 없다. wes 스윕이 세 실행 단위를 따로 부르고, 다음 조건(벡터 있음·점수 다 참·배정 행 있음)을 DB 에서 관측한다. 전부 InvocationType.EVENT, 응답을 기다리지 않는다.
  • 일반 분석은 배치로 실행한다. 임베더는 기본 50장, GPU 워커는 32장, categorize는 갤러리 단위로 실행한다. 관리자 사진 교체는 ExactPhoto로 특정 리비전의 사진 1장만 요청한다.
  • 실패는 한 컬럼. 사진 단위 photo_analysis.error, 잡 단위 ai_analysis_jobs.error. 읽는 쪽 전부가 error IS NULL 을 조건에 넣는다.
  • 재분석 = 데이터 리셋. photo_analysis 행 삭제 + dispatched_at/embed_attempts 초기화. 폴더·추천은 photo_id 로 사진을 가리키므로 안전.
