GPU 워커 실행과 대체 처리

wes는 분석할 사진이 있으면 GPU 워커를 켭니다. 워커는 DB에서 32장씩 직접 선택해 점수를 계산하고, 처리할 사진이 30초 동안 없으면 스스로 종료합니다. GPU를 사용할 수 없거나 진행이 멈추면 score Lambda가 대신 처리합니다.

아키텍처

실선은 호출·저장, 점선은 조회·상태 확인입니다. 박스를 누르면 해당 단계의 설명으로 이동합니다.

제어 규칙 — ScoreWorkerSupervisor.control()

한다5초마다 backlog(점수 없는 UPLOADED)를 세고, 있으면 GPU EC2 를 켜고, 없고 무진행이면 끄며, 워커가 10분 무진행이거나 GPU 가 꺼져 있으면 score Lambda 로 폴백한다. 상태는 인메모리다.왜점수는 CLIP·ARNIQA 세 모델이라 GPU 가 CPU Lambda 보다 수십 배 싸고 빠르지만 켜 둔 채 놀리면 비용이다. 워커가 사진을 스스로 집으므로 wes 는 "켜기·끄기·안 되면 Lambda" 만 결정하면 된다. 정지의 1차는 워커의 유휴 30초 자기 정지이고 wes 의 2분은 안전망이다.없으면GPU 가 켜진 채 방치되거나(비용), 워커가 죽었을 때 점수가 영영 안 나와 잡이 CATEGORIZING 으로 못 넘어간다.입출력카운트 → StartInstances / StopInstances 또는 StageCall.Score(galleryId, photoIds[50])

상태는 전부 인메모리 필드(lastScored · lastProgressAt · deliveringAt · lastStartAt, 갤러리별 fallbackSentAt)다. wes 가 재시작하면 유예가 처음부터 다시 센다.

  1. backlog 세기. countScoreBacklog() = UPLOADED ∧ clip_embedding IS NULL ∧ error IS NULL(LEFT JOIN 이라 아직 임베딩도 없는 사진 포함). 즉 "앞으로 점수가 필요한 사진 수".
  2. 진행 관측. countScored()(전역 clip_embedding IS NOT NULL)가 지난 걸음보다 늘었으면 lastProgressAt = deliveringAt = now.
  3. 워커풀 활성이면(gpu.enabled ∧ pool.isAvailable) controlWorkers:
    • 켜기 — backlog > 0 ∧ up 없음 ∧ (lastStartAt 없음 ∨ lastStartAt + 5분 < now) → start(). up = state RUNNING 또는 PENDING. 로그 gpu start backlog=N workers=…
    • 끄기(안전망) — backlog == 0 ∧ 워커 up ∧ launchedAt + 5분 지남 ∧ (lastProgressAt ?: launchedAt) + 2분 무진행 → stop(instanceId). 로그 gpu stop instance=… reason=idle-safety-net. 1차 정지는 워커의 유휴 30초 자기 정지이고 이것은 2차다.
    • 부팅 유예(5분) 안의 워커가 있으면 deliveringAt = now 로 폴백 타이머를 미룬다.
  4. backlog 0 이면 deliveringAt = null 하고 끝.
  5. 폴백 판단 isFallbackDue: 워커풀이 비활성이면 즉시 true(매 스윕). 활성이면 deliveringAt 이 없을 때 지금 시각을 찍고 false, 이후 deliveringAt + 10분 < now 면 true. 기준은 fallback-after 하나다.
  6. 폴백 실행 fallback(): isAvailable(Score) 아니면 조용히 return → findGalleryIdsWithUnscoredPhotos()(embedding 있음 ∧ clip 없음 ∧ error 없음) 순회 → 갤러리별 fallbackSentAt + 10분 안이면 skip → 그 갤러리의 미점수 photoIds 전부를 scoreBatchSize(50)로 나눠 StageCallDto.Score EVENT → 성공 시 fallbackSentAt[g] = now. 로그 score fallback gallery=G photos=N batches=B. 한 호출이라도 실패하면 이번 폴백 전체 중단.
폴백과 워커가 겹치면
Lambda score 도 UPSERT 라 같은 값을 덮을 뿐이다. 사진마다 "점수 배정 시각"을 두지 않는다. 폴백은 드물다는 전제라 컬럼 없이 갤러리당 10분에 1회로만 억제한다.

ScoreWorkerPool 어댑터

한다EC2(태그로 찾기·켜기·끄기)와 로컬 스크립트를 ScoreWorkerPool 포트 뒤에 숨긴다.왜제어 규칙(언제 켜고 끄나)을 AWS SDK 와 분리해야 로컬에서 같은 규칙을 scripts/gpu/score-worker.sh 로 돌리고 테스트가 인스턴스 없이 규칙을 검증한다.없으면로컬 개발에서 GPU 경로를 확인할 수 없고, 규칙 테스트마다 EC2 를 흉내 내야 한다.

ScoreWorkerSupervisor는 실행 여부를 판단하는 서비스입니다. 외부 인스턴스 조작은 analysis/service/port/ScoreWorkerPool을 통과하며, 상태 조회 결과는 ScoreWorkerDto와 ScoreWorkerStateDto로 전달됩니다.

환경클래스동작
prod (!local)Ec2ScoreWorkerPoolisAvailable = gpu.enabled ∧ gpu.tag 있음. snapshot() = DescribeInstances(Filter tag:Name = wes-score-gpu) → 상태 pending/running/stopping 외는 STOPPED, launchedAt = launchTime. start() 는 STOPPED 인스턴스 하나만 StartInstances(없으면 warn). stop(id) = StopInstances. SDK 예외 → SCORE_WORKER_CONTROL_FAILED(502 PHOTO_502_6). wes EC2 롤에 Describe/Start/Stop 권한 필요

지금 운영 · 실측

  • 2026-09-08 운영 GPU 를 켜서 7,189장을 7.5분에, 2026-09-09 822장을 2분 8초에 점수 냈다(메모리 기록). AI 전달본 시점의 "gpu.enabled=false, Lambda 폴백이 운영 경로"는 그 이전 상태다 — 현재 값은 SSM 에서 확인.
  • 워커 자기 정지가 한때 실패한 원인은 컨테이너에 리전이 없던 것(NoRegionError). 지금은 IMDSv2 placement/region 으로 리전을 얻는다.
  • 워커는 clip_embedding IS NULL 만 보므로 MODEL_VERSION 을 올려도 옛 점수를 다시 집지 않는다. 재점수 절차는 아직 문서화되지 않았다(재분석 = photo_analysis 삭제).
