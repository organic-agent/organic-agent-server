① 브라우저 워커 — 리사이즈 · EXIF · CRC32C

한다원본 JPEG 를 브라우저 워커에서 긴 변 2048 로 줄이고, 회전을 픽셀에 굽고, 원본 EXIF(APP1)를 되살리며, 올릴 바이트의 CRC32C 를 계산한다.왜24MP 원본(8~12MB)은 화면·미리보기·AI 분석 어디에도 필요 없고 수천 장 업로드의 시간·전송량을 20배 키운다. EXIF 는 임베더가 S3 파일에서 읽어 촬영 정보를 채우므로 캔버스 재인코딩으로 지워지면 안 되고, CRC 는 서명에 들어가 S3 가 바이트를 검증하게 한다.없으면업로드가 수십 배 느려지고 S3 비용이 늘며, 촬영 시각·카메라 정보가 사라져 연사 판정(카메라·시각 파티션)이 깨진다. 회전 태그를 그대로 두면 임베더의 exif_transpose 가 이미 선 사진을 한 번 더 돌린다.입출력File → {blob, resized, crc32c}
상수 (src/lib/upload/masterSpec.ts)값이유(원문 주석 요약)
MASTER_LONG_EDGE2048화면·미리보기·AI 분석에 충분, 24MP 원본의 1/20

한 장 처리 순서 (masterResize.worker.ts)

onmessage({id, file}):
  if file.type != "image/jpeg": out = {blob: file, resized: false}          # PNG/HEIC 은 원본 그대로
  else:
    hdr = readJpegHeader(앞 256KB)  (truncated 면 전체 재파싱)                  # width/height/APP1(Exif)
    if max(hdr.w, hdr.h) <= 2048: out = {blob: file, resized: false}          # 이미 작으면 손대지 않음
    else:
      bmp = createImageBitmap(file, imageOrientation: "from-image")           # 회전을 픽셀에 굽는다
      canvas = OffscreenCanvas(round(w·s), round(h·s)); imageSmoothingQuality = "high"
      enc = canvas.convertToBlob({type: "image/jpeg", quality: 0.85}); bmp.close()
      out = hdr.exif ? {blob: spliceExif(enc, withUprightOrientation(hdr.exif)), resized: true}
                     : {blob: enc, resized: true}
  crc = base64(bigEndian32(crc32c(out.blob)))                                 # x-amz-checksum-crc32c 값
  postMessage({id, ok: true, blob, resized, crc32c})

EXIF 를 왜 되살리나 (jpegExif.ts)

캔버스로 다시 인코딩한 JPEG 에는 EXIF 가 없다. 촬영 시각·카메라·조리개는 embedder Lambda 가 S3 파일에서 읽어 photos 컬럼을 채우므로, 원본의 APP1(Exif) 세그먼트를 통째로 잘라 새 파일에 붙인다(첫 번째 Exif\0\0 APP1 만, XMP 제외). 서버 API 는 바뀌지 않는다.

Orientation=1 로 치환하는 이유

회전을 픽셀에 굽고 나면 원본의 Orientation(6·8 등)은 거짓이 된다. 그대로 두면 embedder 의 exif_transpose 가 이미 선 사진을 한 번 더 돌린다. IFD0 의 태그 0x0112 값 칸만 1 로 바꾼다.

CRC32C (crc32c.ts)

Castagnoli 다항식 0x82f63b78 테이블 방식 순수 JS. 결과 4바이트를 빅엔디안으로 base64 인코딩 → 헤더 x-amz-checksum-crc32c. 테스트 벡터 "123456789" → "4waSgw==".

② 발급 — POST /galleries/{g}/photos/upload-urls

한다파일 메타(이름·타입·정확한 크기·CRC)를 받아 photos 행(PENDING)을 만들고 파일마다 presigned PUT URL 을 돌려준다. 세션 API 는 없다 — 발급이 곧 행 생성이다.왜이미지 바이트가 서버를 지나지 않게 하려면 브라우저가 S3 에 직접 올려야 하고, 그러려면 서버가 "이 키에, 이 크기·타입·체크섬으로만" 쓸 수 있는 서명을 미리 줘야 한다. 행을 먼저 만들어 두면 통보가 안 와도 서버가 S3 를 확인해 상태를 맞출 수 있다.없으면서버가 원본을 중계해 메모리·대역폭을 먹거나, 아무 바이트나 아무 키에 올릴 수 있는 URL 이 나간다. 행이 없으면 "올렸는데 잊힌" 사진이 생긴다.입출력files[{fileName, contentType, contentLength, crc32c}](≤500) → uploads[{photoId, storageKey, uploadUrl}] + TTL

발급이 곧 사진 행 생성이다. 세션 API 는 없다. 발급을 리사이즈 뒤에 하는 이유는 서명에 Content-Length 정확값이 들어가서다(presigned PUT 은 범위 서명이 불가능하다).

③ 서명 — S3PhotoStorage.presignUpload

한다S3 SDK 로 PUT 요청 하나를 정확한 Content-Type · Content-Length · CRC32C 값까지 포함해 30분짜리 서명 URL 로 만든다.왜presigned PUT 은 헤더를 정확값으로만 서명할 수 있다(범위 서명은 presigned POST 에만 있다). 크기와 체크섬을 서명에 넣어야 URL 을 가진 누군가가 다른 파일을 올리거나 20MB 상한을 넘기지 못한다. cd00eff 가 고친 것처럼 알고리즘만 지정하면 SDK 내부 헤더가 서명돼 모든 PUT 이 403 이 된다.없으면크기·내용 검증 없는 URL 이 나가거나, 서명 방식이 어긋나 업로드 전체가 실패한다.입출력(key, contentType, contentLength, crc32c) → PresignedUploadDto{url, expiresAt}
PutObjectRequest.builder()
    .bucket(bucket).key(key)
    .contentType(contentType)
    .contentLength(contentLength)      // 정확값
    .checksumCRC32C(crc32c)            // 클라이언트가 계산한 "값"을 서명 — 알고리즘만 지정하면 안 됨
PutObjectPresignRequest.signatureDuration(uploadUrlTtl = 30m)
cd00eff 가 고친 것
checksumAlgorithm(CRC32_C) 로 알고리즘만 지정하면 바디 없는 presign 에서 SDK 가 x-amz-sdk-checksum-algorithm 만 서명하고 정작 체크섬 헤더는 서명하지 않아 모든 PUT 이 403 이었다. 그래서 값을 checksumCRC32C(...) 로 넣는다(S3PhotoStorageTest 가 checksumAlgorithm() == null 을 고정). 보정본 업로드·관리자 교체는 contentLength·crc32c 를 비워 서명한다.

SigV4 는 서명되지 않은 x-amz-* 헤더가 있으면 AccessDenied 다. 그래서 프론트는 세 헤더 외에 아무것도 붙이지 않고, 발급에 넣은 blob 객체를 그대로 보낸다(크기·CRC 가 서명값이므로). 값이 다르면 403 SignatureDoesNotMatch, CRC 가 틀리면 400 BadDigest.

④ PUT — 배치 파이프라인 (GalleryWorkspace.upload)

한다브라우저가 100장씩 리사이즈 → 발급 → PUT ×6 병렬 → 50장마다 complete 를 반복한다. 5xx 는 같은 URL 로 백오프 재시도, 4xx 는 같은 바이트로 재발급 1회.왜발급이 리사이즈 뒤여야 서명에 넣을 정확한 크기가 있고, 묶음 k 를 올리는 동안 k+1 을 줄여야 워커와 네트워크가 동시에 일한다. 100장은 첫 PUT 이 빨리 나가는 크기(30MB), 6 은 브라우저 연결 상한이다. 4xx 는 서명 불일치·만료라 재발급이 답이고 5xx 는 S3 쪽이라 재시도가 답이다.없으면500장을 한 번에 발급하면 150MB 를 들고 8초를 기다린 뒤에야 첫 PUT 이 나가고, 만료된 URL 로 무한 재시도하거나 네트워크 오류로 한 장을 영영 잃는다.입출력File[] → 성공 photoId 들 complete, 실패 목록, 끝에 POST /ai-analysis

발급 실패는 묶음 100장 전체가 실패 처리된다(크기 초과·플랜 한도). 워커 크래시는 그 워커가 들고 있던 한 장만 실패시키고 풀은 계속 쓴다. 리사이즈 실패(prepareMaster 거부)도 그 파일만 실패.

⑤ 완료 통보 — POST /photos/complete

한다브라우저가 "올렸다"고 알린 사진들을 UPLOADED 로 바꾼다. 조건 없는 대입이라 재통보는 멱등이고 S3 를 확인하지 않는다.왜임베딩 배정은 UPLOADED 를 본다. 통보를 받는 즉시 상태를 바꿔야 5초 스윕이 바로 첫 배치를 띄운다. HeadObject 를 여기서 하면 통보마다 S3 왕복이 생기고, 통보 자체가 안 올 수도 있으므로 검증은 스윕에 맡긴다.없으면업로드 뒤 임베딩이 1분(보정 스윕 첫 검사)씩 늦어지고, 재통보에 409 가 나면 프론트의 재시도가 깨진다.입출력{photoIds ≤500} → UPLOADED, {count}

{photoIds}(≤500) → requireUploader → 전부 이 갤러리 사진인지(PHOTO_404_1, 전부-아니면-거부) → markUploaded(). 조건 없는 대입이라 재통보는 멱등이고 응답 count 는 요청 장수다. S3 HeadObject 를 하지 않는다 — 통보가 곧 "올렸다"는 선언이고, 검증은 스윕에 맡긴다.

큐가 비면 프론트는 POST /ai-analysis 를 부른다(5. 사진 분류). 이미 도는 잡이 있으면(409_1) 그 잡이 새 사진을 흡수하고, 이미 CATEGORIZING 이면 끝난 뒤 한 번 더 요청하도록 예약한다.

⑥ 보정 — PendingUploadSweeper

한다통보가 오지 않은 PENDING 사진을 발급 1분 뒤부터 S3 HeadObject 로 직접 확인해 UPLOADED 로 올리고, 10분마다 다시 보며, 24시간 없으면 휴지통으로 보낸다.왜프론트가 죽거나 탭이 닫히면 complete 는 오지 않는다. 사진은 S3 에 있는데 행이 PENDING 이면 임베딩도 폴더도 안 된다. 서버가 S3 를 진실로 삼아 상태를 맞추면 프론트가 어떤 상태로 죽어도 파이프라인이 끝까지 간다. 24시간 뒤 휴지통은 못 올린 행을 정리하되 URL(30분 TTL)이 살아 있을 때 지우지 않기 위해서다.없으면탭을 닫은 사용자의 사진이 영원히 "업로드 중"으로 남고, 카운트(livePending·expected)가 맞지 않아 잡이 분류로 못 넘어간다.입출력photos(PENDING) → UPLOADED / touch / deleted_at
