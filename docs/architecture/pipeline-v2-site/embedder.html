미리보기와 이미지 벡터 생성

embedder는 S3의 사진을 읽어 회전 방향을 반영하고, 긴 변 1,024px의 JPEG 미리보기를 만듭니다. 저장한 미리보기로 DINOv3 벡터를 계산하고 촬영 정보(EXIF)를 함께 기록합니다. 다음 분석 단계도 이 미리보기를 사용합니다.

AI repo b473c61 · embedder/embedder/* · Lambda 3008MB · 900s · 예약 동시성 32 · ephemeral 512MB (인프라 modules/analysis)

배치 흐름모델EXIF → photos 컬럼 (metadata.py)쓰는 SQL응답 · 실패 표시상수 (embedder/embedder/config.py)

배치 흐름 — job.run

한다wes 가 보낸 50장을 8장 배치로 돌며 원본을 받아 회전·1024 축소 → previews/ PUT → 올린 그 바이트로 DINOv3 768d 벡터 → EXIF 와 함께 한 트랜잭션 commit 한다.왜미리보기는 파이프라인 전체(score·categorize·wes LLM)가 여는 유일한 파생본이라 임베더가 만드는 것이 자연스럽고, PUT 뒤에 그 바이트로 임베딩해야 "벡터는 있는데 미리보기가 없는" 상태가 구조적으로 없다. 8장마다 commit 하면 Lambda 가 도중에 죽어도 진행이 남는다. EXIF 는 원본을 이미 디코딩해 들고 있는 여기서 읽는 것이 가장 싸다.없으면HEIC·24MP 원본을 score 워커가 매번 디코딩하고, 벡터와 미리보기가 어긋나 워커가 404 를 만나며, 50장 처리 중 타임아웃이면 전부 잃는다.입출력{galleryId, photoIds} → photo_analysis.embedding · photos.preview_key + EXIF, 응답 {processed, failed, stopped, remaining}

실선은 호출·저장, 점선은 조회·상태 확인입니다. 박스를 누르면 해당 단계의 설명으로 이동합니다.

모델

한다DINOv3 ViT-B/16 의 CLS 토큰을 L2 정규화한 768차원 벡터를 만든다. 모델 id·revision 은 고정.왜연사 판정(코사인 ≥ 0.96)과 임베딩 그룹(concat 공간)의 한 축이 이 벡터다. 자기지도 학습 모델이라 라벨 없이도 "같은 장면"을 가깝게 놓고, 정규화해 두면 내적이 곧 코사인이라 뒤 단계 계산이 단순하다. revision 을 고정해야 갤러리 안 벡터가 한 모델에서 나온다.없으면갤러리 안에 두 모델의 벡터가 섞이면 거리 임계값이 무의미해지고 categorize 가 거부한다.

EXIF → photos 컬럼 (metadata.py)

한다회전 전 원본에서 촬영 시각·카메라·노출·조리개·ISO·크기·바이트를 뽑아 photos 컬럼에 COALESCE 로 채운다. 실패해도 사진은 살린다.왜연사 판정은 카메라(make+model)별로 파티션하고 taken_at 순으로 창을 민다. 화면의 촬영 정보와 정렬도 여기서 온다. 이 서버(wes)는 이미지 바이트를 만지지 않으므로 EXIF 를 읽을 수 있는 곳이 임베더뿐이다.없으면연사가 시각 순이 아니라 id 순으로 묶여 다른 순간이 한 클러스터가 되거나, 촬영 정보 화면이 빈다.
컬럼태그비고
taken_atExif IFD DateTimeOriginal → 없으면 DateTime%Y:%m:%d %H:%M:%S, tz 없음
camera_make / camera_modelMake / Model100자 컷, NUL 제거. categorize 연사 파티션 키
exposure_timeExposureTime"1/200" 또는 "2.5", 30자
f_number / isoFNumber / ISOSpeedRatingsfloat / 튜플이면 첫 값
width / heightOrientation ∈ {5,6,7,8} 이면 스왑사람이 보는 방향
byte_size원본 바이트 길이

브라우저가 리사이즈하며 원본 APP1(Exif)을 되살리고 Orientation 을 1 로 바꿔 두므로(2. 업로드), 여기서 exif_transpose 는 이미 선 사진을 다시 돌리지 않는다.

쓰는 SQL — db.store_embeddings (한 트랜잭션)

한다photo_analysis 벡터 두 컬럼을 UPSERT 하고, photos 의 미리보기 키·EXIF 를 WHERE id AND storage_key 조건(CAS)으로 UPDATE 한다. 상태 컬럼은 건드리지 않는다.왜UPSERT 라 wes 가 빈 행을 미리 만들 필요가 없고, 재실행에 안전하다. CAS 는 선별 뒤 관리자가 사진을 교체했거나 휴지통에 보냈으면 0행으로 끝내 오래된 결과가 덮지 않게 한다. status 를 쓰지 않는 것은 "S3 에 있나"만 사진 상태가 답한다는 v2 원칙이다.없으면교체된 사진에 옛 미리보기 키가 들어가거나, 임베더가 상태를 쓰면 상태 enum 이 실행기마다 늘어난다.
INSERT INTO photo_analysis (photo_id, embedding, embedding_model, created_at, updated_at)
VALUES (…, now(), now())
ON CONFLICT (photo_id) DO UPDATE SET embedding = EXCLUDED.embedding, embedding_model = EXCLUDED.embedding_model,
    version = photo_analysis.version + 1, updated_at = now();
-- 벡터 두 컬럼만. score·categorize 컬럼은 건드리지 않는다

UPDATE photos SET preview_key = %s,
    taken_at = COALESCE(%s, taken_at), camera_make = COALESCE(…), … , byte_size = COALESCE(…),
    version = version + 1, updated_at = now()
WHERE id = %s AND storage_key = %s AND deleted_at IS NULL
  AND EXISTS (SELECT 1 FROM galleries g WHERE g.id = photos.gallery_id AND g.deleted_at IS NULL);
-- CAS: 선별 뒤 사진 교체·휴지통이면 0행. status 는 SET 절에 없다
"preview_key 있음 = 임베딩 있음"
두 문장이 같은 commit 에 묶이므로 이 등식이 성립한다. 그래서 wes 는 PhotoStatus 에 EMBEDDED 를 두지 않고, score 워커·categorize 는 preview_key IS NOT NULL 을 조건으로 쓴다.

응답 · 실패 표시

{ galleryId, photoIds: 50, targets, processed, failed: [storage_key…], metadataFailed: [storage_key…],
  stopped, remaining, elapsedSeconds }
  • processed = photos UPDATE rowcount 누적. remaining = targets − attempted.
  • embedder 는 photo_analysis.error 도 photos.dispatched_at 도 쓰지 않는다. 실패는 응답의 failed[](CloudWatch)뿐이고, 되돌림·상한 표시(EMBED_ATTEMPTS_EXCEEDED)는 wes 스윕 몫이다(3.). wes 계획서의 "임베더가 결정적 실패 시 error 를 쓴다"는 아직 구현되지 않았다.
  • EVENT 호출이라 wes 는 응답을 받지 않는다. 진행은 DB 에서 관측.

관리자 사진 교체 요청

서버는 일반 배치(Embed)와 관리자 사진 교체(ExactPhoto)를 같은 StageInvoker로 전달합니다. 일반 배치는 {galleryId, photoIds}, 관리자 교체는 {jobId, attemptCount, jobType, photoId, galleryId, storageKey, revisionId}입니다. jobId가 있는 요청은 관리자 처리 경로로 분기하므로 일반 배치에 이 키를 추가하면 안 됩니다.

서버 연동 기준은 main@1503a9a입니다. 로컬 대역은 관리자 교체를 지원하지 않습니다. 호출 흐름과 필드별 설명 보기 →
