잡 실행 — wes 안의 스레드 풀이 집고, 조건부 UPDATE 가 이중 실행을 막는다

추천 잡은 Lambda 로 나가지 않는다. 요청 커밋 직후 Launcher 가 스레드 풀(2개)에 넣고, 30초 스윕과 기동 복구가 놓친 잡을 다시 줄 세운다. 어느 경로로 들어오든 claim(PENDING → RUNNING 조건부 UPDATE)이 0행이면 물러나므로 같은 잡이 두 번 돌지 않는다. 실행 중 프로세스가 죽으면 round 유무로 어디까지 갔는지 안다.

recommendation/service/AiSelectionJobLauncher.kt · support/AiSelectionJobRecovery.kt · support/ThreadPoolAiJobExecutor.kt · service/AiSelectionJobRunner.kt:72-174

구동 경로

PENDING→ claim →RUNNING→DONE│FAILED│ 기동 복구 → PENDING (round 있으면 이유만 다시)

세 진입점, 한 관문

한다Launcher 는 잡 id 를 스레드 풀에 넣고, Recovery 는 30초마다 PENDING 을 다시 줄 세우며 기동 때 RUNNING 을 PENDING 으로 되돌린다. claim 은 "PENDING 인 행만 RUNNING 으로" 바꾸는 조건부 UPDATE 로 실제 실행권을 준다.왜실행이 서버 프로세스 안에서 도니 프로세스가 죽거나 큐가 넘치면 잡이 사라질 수 있다. 세 입구는 각각 "지금 바로", "놓친 것 줍기", "죽은 것 되살리기"를 맡고, 그 셋이 겹쳐도 claim 이 한 번만 통과시켜 이중 실행을 막는다. 데드락·분산 락 없이 UPDATE 한 줄로 끝나는 가장 단순한 배타 제어다.없으면PENDING 잡이 영원히 남거나, 즉시 실행과 스윕이 같은 잡을 두 번 돌려 같은 라운드에 추천이 두 벌 생긴다(UNIQUE (selection, round, photo) 위반). 기동 복구가 없으면 죽은 RUNNING 잡이 "계산 중"으로 굳는다.

run(jobId) 골격

한다잡 한 번의 전체 순서를 고정한다: 집기 → (복구면 이유만) → 질의 해석 → 재료 읽기 → 계획 → 1단계 저장 → 2단계 이유 → 닫기. 단계마다 짧은 트랜잭션을 열고, LLM 은 트랜잭션 밖에서 부르며, 예외는 잡을 FAILED 로 닫는다.왜무거운 단계(LLM 수십 초)와 DB 쓰기를 분리해야 커넥션을 오래 잡지 않고, 단계 사이에 죽어도 다음 실행이 어디서 이어갈지 판단할 수 있다. 예외를 잡을 FAILED 로 바꾸는 것도 여기다 — 화면이 "실패"를 알고 폴링을 멈추게.없으면한 트랜잭션에 전부 넣으면 LLM 3분 동안 커넥션을 물고 있고, 도중에 죽으면 추천 행이 롤백돼 화면에 떴던 칩이 사라진다. 예외를 삼키면 잡이 RUNNING 으로 굳는다.
if claim(jobId, now) == 0: return
timing = StageTiming()
saved = loadSavedRound(jobId)                     // job.round != null 이면 1단계는 이미 끝난 잡
if saved != null: finishSavedRound(saved)          // fillReasons 만 다시 → finish(recovered=true) ; return
resolveQuery(jobId, timing)                        // 4. prompt·targetCount 있을 때만 Bedrock (트랜잭션 밖)
world = timing.measure("load")    { load(jobId) }  // 5.
draft = timing.measure("plan")    { plan(world) }
round = timing.measure("persist") { persistRound(world, draft) }      // 1단계 — 여기서 화면에 칩이 뜬다
timing.measure("reasons") { fillReasons(world, draft, round, timing) } // 2단계 — 6.
job.finish(summary(world, draft, round, reasonReady, timing), now)
log.info("AI 추천 잡 완료: jobId={}, round={}, k={}")
catch (e): log.error("AI 추천 잡 실패: jobId={}", e); job.fail("${e::class.simpleName}: ${e.message}", now)

각 단계는 자기 트랜잭션(TransactionTemplate)으로 짧게 열고 닫는다. LLM 호출(질의 해석·이유 문장)은 트랜잭션 밖에서 돈다 — DB 커넥션을 수십 초 붙들지 않기 위해서다.

복구 — round 가 있으면 이유만

한다다시 집은 잡의 round 를 보고 어디까지 갔는지 판단한다. round 가 있으면 추천은 이미 저장된 것이니 이유 문장만 이어서 채우고, 없으면 처음부터 한다.왜1단계(순위)는 확정되는 순간 화면에 보이고 사용자가 그걸 보고 담기 시작할 수 있다. 복구가 순위를 다시 뽑으면 방금 본 추천이 바뀐다. 그래서 assignRound 를 1단계와 같은 트랜잭션에 묶어 "round 있음 = 순위 확정"이라는 하나의 표시로 삼는다.없으면죽었다 살아난 잡이 추천을 다시 뽑아 칩이 뒤바뀌거나, 반대로 이유가 영영 비어 있는 채로 DONE 이 된다.

persistRound 가 job.assignRound(round) 를 같은 트랜잭션에서 찍으므로, 실행 중 죽은 잡은 round 로 두 경우가 갈린다.

finish · fail · result

한다잡을 닫는다. 성공이면 DONE 과 함께 이번 라운드의 요약(result)을, 실패면 FAILED 와 예외 문자열을 남긴다.왜추천 결과 자체는 ai_recommendations 에 있지만 "왜 이 장수인가"(쿼터·제외·이상치·요청 부족분)와 "얼마나 걸렸나"는 행에 없다. 운영자가 로그를 뒤지지 않고 잡 한 행으로 판단할 수 있게 요약을 jsonb 로 남긴다. 화면에는 k·shortfallCount 만 나간다.없으면추천이 적게 나왔을 때 이상치 제외 때문인지 후보 부족인지 알 길이 없고, 실패 원인이 로그에만 남아 잡 행을 봐도 왜 실패했는지 모른다.
