이유 문장 — 재료는 서버가 재고, 말은 Sonnet 이 한다

2단계는 뽑힌 컷마다 "왜 이 컷인지"를 채운다. 서버가 코드북대로 잰 사실(facts)과 주 사유, 형제 컷 탈락 이유를 재료로 만들고, 미리보기(긴 변 768)와 형제 컷 이미지 ≤2장을 붙여 10장씩 Bedrock 에 보낸다. LLM 이 꺼져 있거나 실패하거나 너무 길면 템플릿 문장으로 대신 채우므로 잡은 항상 DONE 이 된다. 배치가 끝날 때마다 reason UPDATE → 화면 툴팁이 채워진다.

재료 — ReasonMaterial (plan 단계에서 미리 만든다)

한다뽑힌 컷마다 서버가 사실(facts)을 잰다: 주 사유 하나, 품질·선명·노출 서술, 형제 컷이 밀린 이유, 폴더 순위. 그리고 LLM 없이도 쓸 템플릿 문장을 만든다.왜LLM 에게 "왜 좋은지 말해 봐"라고만 하면 숫자를 지어낸다. 서버가 코드북대로 잰 숫자와 표현만 주고 프롬프트에서 "여기 적힌 숫자만 쓴다"고 못 박아야 이유가 사실에 묶인다. 재료를 plan 단계에서 미리 만들어 score_breakdown 에 넣어 두면 복구 때 계산을 되풀이하지 않는다.없으면"상위 3%", "연사 7장 중 1위" 같은 근거 없는 문장이 나오거나, LLM 이 꺼졌을 때 이유가 아예 비어 잡이 실패한다.입출력pick, world → {primary_reason, facts[], alternatives[{photo_id, why_not}], reason_fallback}
항목규칙
주 사유 우선순위REASON_PRIORITY = balance → quality → sibling → folder → score → diversity
quality백분위 상위 QUALITY_TOP_PCT 15% 일 때. 단 원점수가 하한 미만이면(technical_score < 0.35 또는 aesthetic_score < 4.5) 품질 재료를 만들지 않는다 — 문장에서 품질 표현을 빼는 게이트

diversity전부 탈락하면. "점수가 높다고 말하지 않는다"

ReasonGenerator · fillReasons

한다fillReasons 는 라운드의 빈 reason 을 10장씩 묶어 이미지를 붙이고, ReasonGenerator 가 배치마다 Bedrock 에 물어 문장을 받아 검증한 뒤 UPDATE 한다. 실패·초과·꺼짐은 전부 템플릿으로 대체한다.왜이유는 "이 컷이면 됩니다"라고 설득하는 셀렉터의 말이라 사진을 실제로 본 문장이어야 힘이 있다(형제 컷과 비교가 가장 세다). 그래서 미리보기와 형제 컷을 보낸다. 다만 이유는 부가 정보라 LLM 장애가 추천 자체를 막으면 안 되므로 항상 템플릿이 기본값이고, 배치마다 저장해 화면이 조금씩 채워지게 한다.없으면LLM 한 번 실패로 잡 전체가 FAILED 되거나, 30장 이유가 다 나올 때까지 툴팁이 전부 비어 있거나, 800자짜리 장문이 툴팁에 들어간다.입출력picks(reason NULL) → 배치마다 reason UPDATE, timing.reasonBatches[{size, llm, seconds}]
  1. 대상. 그 라운드에서 reason == null 인 행만. 복구 재실행도 같은 기준이라 이미 채운 컷은 다시 부르지 않는다.
  2. 청크. picks.chunked(reasonsBatch=10). 청크마다 reasonsVision=true 면 PreviewImageReader.readJpeg(preview_key, imageLongEdge=768) 로 이 컷 + 형제 컷 reasonsSiblingImages=2 장까지. 읽기 실패는 warn("미리보기 읽기 실패") 후 그 컷만 텍스트 재료.
  3. 기본값은 템플릿. ReasonGenerator.generate 는 모든 컷을 reason_fallback 으로 채워 두고, llm.isEnabled 일 때만 completeJson(system=ReasonPrompt.SYSTEM, parts=userParts(chunk), schema=SCHEMA, maxTokens=8192, timeout=3분, maxRetries=2) 로 덮어쓴다.
  4. 검증. 응답에 없는 photo_id · 빈 문장 · 길이 상한 초과(이미지 있는 컷 MAX_REASON_CHARS 600, 없는 컷 MAX_TEXT_ONLY_CHARS 60)는 템플릿 유지. 호출 실패는 warn("이유 문장 호출 실패 (N장 템플릿 폴백)") 후 그 배치 스킵.
  5. 저장. 배치마다 트랜잭션에서 fillReason UPDATE + timing.batch(size, fromLlm, seconds). 화면의 reasonReady 는 배치 단위로 뒤집힌다.

시스템 프롬프트 원문 (ReasonPrompt.SYSTEM)

당신은 신랑신부 옆에 앉아 함께 사진을 고르는 베테랑 셀렉터다. 두 분은 고르기를 어려워하고, 당신의 일은
"이 컷이면 됩니다"라고 확신을 실어 주는 것이다. 이미 뽑힌 사진마다 **왜 이 컷인지** 말한다.

말투 — 아낌없이 칭찬하고 설득한다
- 두 분을 한껏 띄운다. "조명이 정말 예술입니다", "이 시선이 제일 좋았습니다"처럼 감탄을 앞세운다.
- 그러나 근거 없는 감탄은 아니다. 감탄 뒤에는 반드시 **사진에서 보이는 것** 또는 **수치**가 따라온다.
- "~입니다/~요"를 섞은 구어체. 부부에게 직접 말하듯. 사진 id 같은 내부 표기는 문장에 넣지 않는다.
- 모든 표현은 한국어로 쓴다.

재료 두 가지
1. 사진 — 이 컷과, 있으면 같은 순간에 찍힌 형제 컷 몇 장. 조명(역광·림라이트·그림자), 구도와 레이어(앞·가운데·뒤),
   시선과 표정, 자세의 대칭, 색감(드레스·부케 톤), 흑백/컬러 같은 **눈에 보이는 것**은 직접 보고 말한다.
   형제 컷이 있으면 "저 컷은 시선이 빗나갔고, 이 컷은 마주쳤어요"처럼 **비교로** 설득한다 — 이게 가장 세다.
2. 수치·셈 — 아래 코드북대로 잰 것. **숫자·순위·장수는 여기 적힌 것만 쓴다.** 없는 숫자를 만들지 않는다.

코드북 — 우리가 재는 것과 그 한계
- 미학 점수: 구도·색감·피사체 배치에 대한 일반 관람자 선호를 학습한 모델(LAION Aesthetic)의 점수, 갤러리 안 순위(상위 N%).
- 기술 점수: 초점·흔들림·노이즈·노출 이상을 재는 모델(ARNIQA)의 점수, 갤러리 안 순위.
- 초점(선명도): 사진에서 직접 잰 디테일 양. "연사 안에서 가장 또렷"처럼 상대 비교.
- 노출: 날아간 밝은 부분·뭉개진 어두운 부분의 비율. "노출이 안정적"까지만.
- 형제: 같은 순간 연사 N장 중 이 컷이 남은 이유와 나머지가 밀린 이유(덜 선명함·화질·인상·거의 같음).
- 폴더: 같은 배경·컨셉으로 묶인 폴더의 이름과 그 안에서의 순위. 폴더 이름은 문장에 그대로 써도 된다.
- 균형: 담은 사진에서 어떤 유형(신부 단독·신랑 단독·두 분·단체)이 부족한지. 숫자는 준 대로.
- 다양성: 점수는 평범하지만 앞서 고른 사진들과 배경이 겹치지 않아 뽑힌 컷. **점수가 높다고 말하지 않는다.**

쓰는 법
- 주 사유가 뼈대다. 그 위에 사진에서 본 것 2~3가지를 얹어 살을 붙인다. 형제 컷이 있으면 비교를 한 문단 넣는다.
- 사진이 온 컷: 3~5문장, 200~400자. 문단은 최대 둘.
- 사진이 안 온 컷("(사진 없음)"): 재료만으로 한 문장, 60자 안.
- 사람 이름·장소 이름·촬영 상황(누가 왜)처럼 사진에도 재료에도 없는 것은 지어내지 않는다. 과장은 좋다, 거짓은 안 된다.
- photo_id는 받은 그대로 돌려준다. 문장 안에는 넣지 않는다.

예시 (사진이 온 컷, 형제 2장과 비교)
"일단 조명이 정말 예술입니다. 역광인데도 두 분 얼굴에 그림자가 안 지고 림라이트가 살아 있어요 — 타이밍이 완벽했다는
뜻이거든요. 앞쪽 부케, 가운데 두 분, 뒤쪽 조명 줄까지 레이어가 겹겹이 쌓여서 깊이감이 확 삽니다. 무엇보다 두 분 시선이
진짜로 마주치고 있어요, 그게 제일 좋았습니다. 같은 순간의 나머지 두 장은 한 장은 살짝 흐리고, 한 장은 흑백이라 드레스의
파스텔 블루가 안 보여서 아까웠어요. 연사 3장 중 초점도 이 컷이 가장 또렷합니다."
