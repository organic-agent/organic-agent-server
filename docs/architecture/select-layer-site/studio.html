스튜디오 — 워크스페이스가 소유 단위이고, 스튜디오는 그 위의 프로필이다

갤러리·멤버십·인가의 축은 워크스페이스(PERSONAL | STUDIO)다. 스튜디오는 STUDIO 워크스페이스와 PK 를 공유하는 1:1 프로필 테이블(공개 주소·연락처·소개·정지)이고, studio_members 는 테이블이 아니라 workspace_members 의 별칭이다. 작가는 스튜디오를 만들어 직원을 링크로 초대하고, 갤러리를 만들어 사진을 올린 뒤 공개하고, 부부를 링크로 초대한다. 모든 하위 기능(별점·협업·보정·선택)의 인가는 GalleryAccessPolicy 한 클래스가 결정한다.

개념 관계 — 워크스페이스 · 스튜디오 · 갤러리

한다Workspace 가 갤러리와 멤버십을 소유한다. STUDIO 타입이면 Studio 행(공개 프로필)이 같은 PK 로 붙고, PERSONAL 타입이면 소유자 한 명과 파트너가 workspace_members 로 들어간다. 갤러리는 workspace_id 하나로 두 경우를 같이 다룬다.왜스튜디오 작가와 개인 작가(스튜디오 없음)가 같은 갤러리·셀렉 기능을 써야 한다. "소유 단위"를 워크스페이스로 추상화하면 인가(isManager)·초대·알림이 타입 분기 몇 개로 끝나고, 스튜디오 고유의 것(공개 주소·정지)은 프로필 테이블로 분리된다. studio_members 를 별도 테이블로 두지 않은 것도 같은 이유다.없으면개인 작가용 API 를 통째로 복제하거나, 스튜디오 정지가 갤러리 인가에 반영되지 않는다.

스튜디오 API — /api/v1/studios

한다스튜디오를 만들고(생성자가 OWNER), 프로필을 고치고, 직원을 링크로 초대하고, 역할을 바꾸고, 내보내고, 탈퇴하고, 스튜디오를 지운다. 이메일 지정 초대는 없고 수락은 갤러리 초대와 공유하는 POST /api/v1/invites/{token}/accept 가 처리한다.왜작은 스튜디오가 직원을 붙이는 일은 "링크 하나 보내기"면 충분하고, 링크는 7일·활성 1개·인원 무제한으로 단순하게 둔다. 마지막 OWNER 보호(LAST_OWNER_PROTECTED)와 OWNER 강제 해제 금지는 스튜디오가 주인 없이 남지 않게 한다. 삭제는 workspaces 행 삭제 한 번으로 FK CASCADE 가 스튜디오·멤버·갤러리·초대를 함께 지운다.없으면직원마다 계정을 만들어 주거나, 마지막 관리자가 나가 아무도 못 만지는 스튜디오가 남는다.

개인 작가 — 스튜디오 없이

한다PERSONAL 워크스페이스를 로그인·개인 갤러리 개설 시 지연 생성하고(ensurePersonalWorkspace, "{닉네임}의 작업공간"), 갤러리는 POST /galleries/personal 로 결제(test_checkouts)를 소비해 만든다. 파트너는 PERSONAL_PARTNER 초대로 workspace_members(MEMBER) 가 된다.왜혼자 찍고 혼자 고르는 사용자도 있다. 스튜디오 갤러리 생성 API(POST /galleries)는 PERSONAL 워크스페이스에 402 PERSONAL_CHECKOUT_REQUIRED 를 던져 결제 경로로 보낸다. 개인 갤러리는 생성 즉시 OPEN 이고 planExpiresAt · planMaxPhotoCount 가 박혀 플랜 만료 시 스케줄러가 자동 close 한다.없으면개인 사용자가 빈 스튜디오를 만들어야 하거나, 플랜 상한 없이 무제한 업로드가 된다.

개인 갤러리에서 "부부/파트너"는 gallery_members 가 아니라 workspace_members 다. 그래서 정책의 "개인 참가자"(isPersonalParticipant)는 PERSONAL 워크스페이스의 아무 멤버이고, 보정 처리(requireRetouchProcessor)도 개인 갤러리에서는 참가자 본인이 한다.

갤러리 — 생성 · 상태 · 상한

한다작가가 {workspaceId, title, selectionDeadline?, maxSelectablePhotoCount?, maxRetouchRoundCount?, shootType} 로 갤러리를 만들면 status=DRAFT · stage=UPLOAD 로 시작하고 빈 셀렉 앨범이 같이 INSERT 된다. 사진을 올리고 분석·폴더 정리를 마친 뒤 open() 하면 부부가 볼 수 있다.왜갤러리는 "한 촬영의 셀렉 계약"이라 계약 조건(장수·마감·보정 횟수)이 갤러리에 있다. 세 상태 축이 따로 있는 이유가 다르다 — status 는 부부의 열람·선택 가능 여부, stage 는 작가 화면의 진행 스테퍼, workflowStatus 는 자유 태그. 앨범을 갤러리 생성 시 함께 만드는 것은 조회가 행을 만들지 않게 하려는 것이다.없으면DRAFT 상태에서 부부가 미완성 갤러리를 보거나, 계약 장수가 셀렉·보정에 흩어져 관리된다.

부부 초대 — GalleryInvite

한다작가가 갤러리 초대 링크(kind=GALLERY_MEMBER, maxUses 기본 2, 7일, 활성 1개)를 발급하고, 신랑·신부가 각자 링크로 로그인·미리보기·수락하면 gallery_members 행이 생긴다(정원 2). 개인 갤러리는 PERSONAL_PARTNER 초대로 workspace_members 에 들어간다.왜부부는 공동 계정이 없으므로 각자 로그인해야 하고, 링크만 있으면 되도록 토큰이 OAuth state 를 타고 콜백까지 살아남는다. 담당 작가가 자기 갤러리 초대를 수락하지 못하게(requireNotManager) 막는 것은 "작가는 고객 대신 고를 수 없다"는 원칙이다. 초대 종류를 워크스페이스 타입에 묶어(validateKind) 스튜디오 갤러리에 파트너 초대가 섞이지 않게 한다.없으면작가가 부부 계정을 대신 만들거나, 초대 링크가 무한히 재사용된다.입출력POST /galleries/{g}/invites {kind?, maxUses?, expiresAt?} → inviteUrl = app.invite.base-url + "/" + token · POST /invites/{token}/accept → 멤버 행

GalleryAccessPolicy — 모든 하위 기능의 공통 관문

한다"누가 작가인가(isManager: STUDIO 멤버 ∧ 정지 아님, 또는 PERSONAL 소유자)", "누가 부부인가(gallery_members)", "누가 개인 참가자인가"를 한 곳에서 판정하고, 기능별 require* 메서드로 노출한다. 갤러리 상태·마감·플랜 검사(requireWritable · requireSelectable)도 여기 붙는다.왜설계 원칙 둘을 코드 한 곳에 못 박기 위해서다 — 작가는 고객 대신 사진을 고를 수 없다(requireSelectionEditor 가 스튜디오 멤버를 명시 거부), 부부의 사적 정보(별점·댓글·하객 의견)는 작가에게 비공개(requireParticipant* 가 스튜디오 멤버 거부). 서비스마다 멤버십 쿼리를 쓰면 이 원칙이 한 곳에서 깨진다.없으면작가가 부부 계정 없이 담기를 누르거나, 하객 의견이 작가 화면에 보인다.
