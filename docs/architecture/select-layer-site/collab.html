협업 셀렉 — 부부가 공유폴더 링크를 만들고, 하객이 로그인 없이 좋아요·댓글을 남긴다

협업 세션(collab_sessions)은 갤러리당 여러 개 만들 수 있는 공유폴더 링크다. 사진 목록은 컨셉 폴더에 동적으로 연결하거나(CONCEPT_FOLDER) 직접 고른 스냅샷(MANUAL)이고, 하객은 닉네임만 등록하면 서버가 준 게스트 토큰으로 좋아요·댓글을 남긴다. 7일 만료·폐기·재발행이 있고 실시간 채널은 없다(폴링). 협업 결과가 셀렉 앨범에 자동 반영되는 경로는 없다 — 부부가 좋아요 수를 보고 직접 담는다. 작가에게는 링크·의견 모두 비공개다.

세션 관리 — CollabSessionService (부부)

한다공유폴더를 만들고(컨셉 연결 또는 사진 직접 지정), 이름·표지를 바꾸고, 링크를 폐기하거나 새 토큰으로 재발행하며, MANUAL 폴더에 사진을 넣고 뺀다. 같은 컨셉에 이미 세션이 있으면 새로 만들지 않고 재발행해 돌려준다(멱등).왜부부가 가족·친구에게 "이 폴더 좀 봐 줘"를 보내는 기능이라 로그인 없는 링크가 필요하고, 링크는 언젠가 새어 나가므로 만료·폐기·재발행이 있어야 한다. 컨셉 폴더에 동적으로 붙는 모드는 AI 폴더를 그대로 공유하는 흔한 경우를 한 번의 클릭으로 만들고, MANUAL 은 "이 30장만"을 위한 것이다. 작가를 거부하는 것은 하객 의견이 부부의 사적 공간이기 때문이다.없으면부부가 사진을 내려받아 카톡으로 뿌리고 의견을 모아 다시 타이핑한다. 링크를 회수할 수 없다.입출력POST {conceptFolderId? | photoIds[≤200], name, coverTitle?, includeAllAlbums?} → CollabSessionResponse{sessionId, collabUrl, selectionMode, photoCount, expiresAt, …}

하객 경로 — CollabGuestService (/api/v1/collab/{collabToken}, permitAll)

한다링크만으로 랜딩을 보여주고, 닉네임을 받아 게스트 토큰을 발급하며, 그 토큰(X-Guest-Token 헤더)으로 좋아요·댓글을 받는다. JWT 가 있으면 로그인 참여자로 자동 등록한다(Bearer 우선).왜하객에게 회원가입을 시키면 아무도 참여하지 않는다. 대신 서버가 토큰을 발급해 "누가 눌렀는지"를 참여자 행으로 구분하고, 로그인 사용자(부부 본인·파트너)도 같은 참여자 모델에 올려 집계 코드를 하나로 둔다. 입장은 requireReadable 만 지나므로 마감된 갤러리에서도 보기·닉네임 등록은 되고 반응만 막힌다.없으면좋아요를 누가 눌렀는지 구분할 수 없어 멱등·취소가 불가능하고, 부부 본인의 반응이 하객 통계와 섞인다.입출력POST /guests {nickname} → {guestToken, participantId, participantType} · PUT/DELETE /photos/{p}/like → 204 · POST /photos/{p}/comments {content} → 201

세 개의 문 — CollabSessionAccess

한다requireReadable(폐기 → 410_1, 만료 → 410_2, DRAFT 갤러리 → 403_1), requireWritable(+ 갤러리가 OPEN ∧ 마감 전 ∧ !ARCHIVED ∧ 플랜 유효, 아니면 FEEDBACK_CLOSED 403_2), requireParticipant(JWT → USER 참여자 자동 생성, 스튜디오 멤버면 PARTICIPANT_READ_ONLY 403_4; 아니면 게스트 토큰, 없으면 401_1).왜링크 하나로 들어오는 경로라 "볼 수 있는가 / 반응할 수 있는가 / 누구인가"를 세 단계로 나눠야 마감 뒤에도 보기는 되고, 작가는 봐도 반응은 못 하며, 익명이라도 취소·삭제가 본인 것에만 되는 규칙을 한 곳에서 지킬 수 있다. 락 순서를 사진 → 세션으로 고정한 이유는 사진 삭제 트랜잭션과의 데드락 회피다.없으면폐기한 링크가 계속 열리거나, 마감 뒤에 하객이 의견을 바꾸거나, 작가가 자기 갤러리의 하객 의견에 끼어든다.
writable = gallery.status == OPEN ∧ !deadlinePassed ∧ stage != ARCHIVED ∧ planExpiresAt 미래
readable 은 writable 이 false 여도 유지 — 보기·입장은 되고 좋아요·댓글만 403 COLLAB_403_2

사진 집합 · 집계 — 두 모드가 한 쿼리

한다CollabSessionPhotoRepository.findSharedPhotos 네이티브 쿼리 하나가 concept_folder_id 유무로 분기해 MANUAL 멤버십 또는 컨셉→세부→배정 조인을 돌려준다(PENDING·휴지통 제외, display_order 순). 좋아요·댓글 수는 GROUP BY 두 번, liked 는 참여자가 있을 때만.왜모든 화면과 인가(COLLAB_404_2 판정)가 같은 집합을 봐야 한다. 두 모드를 한 쿼리에 두면 "컨셉 모드에서는 보이는데 좋아요는 404" 같은 어긋남이 없다. 집계를 조회 시점에 하고 저장하지 않는 것은 실시간 채널이 없어 폴링마다 정확한 값을 주는 편이 단순하기 때문이다.없으면모드별 코드 경로가 갈려 한쪽만 고쳐지고, 캐시된 좋아요 수가 취소를 반영하지 못한다.

페이징은 메모리 슬라이싱(전체 photoId 를 읽어 subList, size 1~200 clamp). 컨셉 폴더에서 사진이 나가면 CollabCategoryReactionCleaner 가 그 세션의 좋아요·댓글을 지우고, 컨셉이 삭제되면 세션을 soft delete 한다.

실시간성 · 셀렉 반영 · 접점

  • SSE·WebSocket 없음. 하객 화면은 presigned URL TTL 기반 타이머(clamp(ttl×0.8, 1s, …))와 focus/visibilitychange 로 재조회, 워크스페이스는 4분 간격 폴링. 서버가 주는 힌트는 viewUrlTtlSeconds 뿐.
  • 셀렉 앨범 자동 반영 없음. selection 패키지에 collab 참조 0건, 역방향도 0건. 부부가 likeCount 를 보고 담기 API 를 따로 부른다. CollabSelectionMode 는 공유 목록 구성 방식일 뿐이다.
  • 알림 없음. 하객 좋아요·댓글은 user_notifications 를 만들지 않는다. 활동 기록(ActivityRecorder)은 모든 성공 변경에 남는다.
  • 휴지통. 좋아요 취소·댓글 삭제는 ProductChildTrashService 로 soft delete(7일). 관리자 AdminChildTrashType.COLLAB_COMMENT / COLLAB_LIKE.
  • 보안 설정. PublicPaths 의 /api/v1/collab/** permitAll. collab/config 에는 app.collab.base-url(프론트 주소, 링크 조립)만.
