담기 · 빼기 — select() / deselect()

한다부부가 고른 사진을 앨범에 넣고 뺀다. 검증 순서는 권한 → 갤러리 행 락 → 내보내기 뒤 잠금 → 폴더 정리 필수 → 앨범 생성·편집 가능 → 사진 유효성 → 중복 먼저, 그다음 상한 → sort_order 부여 → 저장 → 활동 기록.왜담기는 여러 사람(신랑·신부)이 동시에 누를 수 있어 갤러리 행을 잠가 직렬화한다. 중복을 먼저 걸러야 "상한 초과 N장"이 실제와 같다. 부분 성공을 두지 않는 것은 화면이 "몇 장은 들어갔고 몇 장은 아닌" 상태를 설명할 수 없기 때문이다. 보정본으로 담아도 photo_id 는 원본이라야 중복·정원 규칙이 산다.없으면두 사람이 같은 순간 담으면 정원이 넘거나 같은 사진이 두 번 들어가고, 보정본을 따로 세면 같은 사진이 원본·보정본으로 두 자리를 차지한다.입출력{photoIds, retouchPhotos} → photo_selection_items INSERT(원본 photo_id, sort_order, retouch_photo_id) · 400/409 코드
  1. 인가. requireSelectionEditor — 초대된 부부 또는 개인 갤러리 참가자만. 스튜디오 워크스페이스 멤버(작가)는 명시적으로 거부. 안에서 requireSelectable(쓰기 가능 ∧ 마감 전 ∧ OPEN).
  2. 갤러리 행 락. 앨범 행은 아직 없을 수 있어 갤러리 행을 requireWithLockById 로 잠근다.
  3. 내보내기 뒤 잠금. 개인 갤러리이고 stage 가 RETOUCH/DELIVERY/ARCHIVED 면 SELECTION_ALREADY_EXPORTED.
  4. 폴더 정리 필수. photoOrganizationRequired ∧ foldersSavedAt == null → PHOTO_ORGANIZATION_REQUIRED.
  5. 앨범. loadOrCreate(V5 이전 갤러리 대비) → requireEditable(SUBMITTED 면 409).
  6. 사진 검증. 빈 목록 · 배치 상한(app.storage.max-batch-size) · 갤러리 밖 · PENDING → 400. 보정본은 RetouchResultLoader.validateSelectable.
  7. 중복 → 상한. requireNotSelected → requireWithinMax(maxSelectablePhotoCount, 기존+신규). null 이면 무제한.
  8. 저장. sort_order = (max ?: −1) + 1 + index, added_by_user_id, retouch_photo_id. activityRecorder.recordGallery(MANDATORY 전파).

제출 · 취소 — submit() / withdraw()

한다앨범을 SUBMITTED 로 잠그고 갤러리 stage 를 SELECTION_COMPLETED 로 옮기며, 1회차 보정 요청을 같은 트랜잭션에서 만들고 작가(워크스페이스 멤버)에게 알린다. 취소는 작가만, 보정이 진행되지 않았을 때만.왜제출은 "부부의 선택이 끝났다"는 계약 행위라 계약 장수와 정확히 맞아야 하고(requireExactTarget), 그 뒤 작가의 보정 작업이 시작된다. 보정 요청을 제출과 묶는 것은 "제출했는데 보정 요청이 없는" 중간 상태를 없애기 위해서다. 취소 권한이 작가에게만 있는 것은 이미 보정에 들어간 작업을 부부가 무효화하지 못하게 하려는 것이다.없으면29장으로 제출되거나, 제출 뒤에도 부부가 담기·빼기를 계속해 작가가 어떤 목록을 보정해야 할지 모른다. 보정 결과물이 있는데 취소되면 결과물이 고아가 된다.입출력submit(requests?) → SUBMITTED · galleries.stage · retouch_rounds(1회차) · 알림 / withdraw() → SELECTING · SELECTION_REOPENED 알림(갤러리 멤버)
submit:
  requireSelectionEditor; if personalGallery → 409 SELECTION_409_6 (개인 갤러리는 export 가 제출)
  lock gallery; requireSelectionNotExported; selection ?: 400 EMPTY_SELECTION
  photos = 실제 남아 있는 사진(휴지통 제외)            // 항목 행 수가 아니라
  requireEditable; requireExactTarget(gallery.maxSelectablePhotoCount, photos.size)   // 0장 → 400_6, 불일치 → 400_7
  selection.submit(user, now)
  latestRound = 최신 보정 회차
  if latestRound == null || latestRound.isDrafting: RetouchRequestService.submit(roundNo = latest?.roundNo ?: 1, photoIds = 전부, requests)
  else if requests 비어 있지 않음: RetouchException(INVALID_ROUND_STATUS)
  gallery.markSelectionCompleted()                     // stage = SELECTION_COMPLETED
  recordGallery; notify(SELECTION_SUBMITTED → workspace_members 전원)

withdraw (requireManager):
  lock gallery; latestRound COMPLETED → 409; REQUESTED ∧ 결과물 있음 → 409; REQUESTED ∧ 결과물 없음 → reopenRequest()
  selection.withdraw(); gallery.markSelectionInProgress(); notify(SELECTION_REOPENED → gallery_members)

다른 기능과의 접점

  • AI 추천 — ai_recommendations.selection_id → photo_selections CASCADE. 추천 요청이 앨범을 없으면 만들고 requireEditable. 응답 selected 는 항목 포함 여부. accepted_at 훅은 미구현.
  • 협업 — 앨범과 직접 연결되지 않는다. CollabSelectionMode 는 세션의 사진 구성 방식(MANUAL / CONCEPT_FOLDER)일 뿐이고 하객에게는 별점이 숨겨진다. 2.
  • 보정 — retouch_photo_id(SET NULL)로 보정본을 담고, 제출이 1회차 요청을 만들며, 회차 제출은 앨범 제출을 전제한다. 3.
  • 관리자 — 리소스 SELECTION(읽기 전용 status), 워크플로 REPLACE_SELECTION_ITEMS · SUBMIT_SELECTION_REVISION · WITHDRAW_SELECTION · CREATE_AI_SELECTION_DRAFT.
