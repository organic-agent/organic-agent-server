보정 — 회차 단위로 요청을 모으고, 작가가 결과를 올리고, 부부가 확정한다

보정은 회차(retouch_rounds, 갤러리당 1..N)로 돈다. 부부가 사진에 좌표 포인트와 요청문을 달아 회차를 제출하면(보통 셀렉 제출이 1회차를 함께 만든다) 작가 차례가 되고, 작가가 결과 파일을 S3 에 직접 올려 "보내기"를 누르면 회차가 끝나며, 부부가 "확정"하면 갤러리가 보관(ARCHIVED)으로 간다. 보정본은 photos 행이 되지 않는다 — 미리보기도 임베딩도 없고, 셀렉 항목에 retouch_photo_id 로만 매달린다.

개념뜻규칙
RetouchRound부부가 보정 요청을 모아 일괄 제출하는 단위이자 계약의 "보정 N회"를 세는 단위. 갤러리당 1..N(셀렉당 아님)(gallery_id, round_no) 유니크. COMPLETED 가 아닌 회차는 한 번에 하나(갤러리 행 락으로 보장). 상태 DRAFTING → REQUESTED → COMPLETED, reopenRequest(REQUESTED→DRAFTING)
RetouchPhoto이름과 달리 "보정본 사진"이 아니라 회차에 담긴 요청 한 건. 요청(문구·포인트)과 결과(result_key)가 한 행부분 유니크 (round_id, photo_id) WHERE deleted_at IS NULL. request_text ≤2000, request_points ≤100, result_key · result_content_type. 항목 상태 컬럼 없음 — hasResult = result_key != null
RetouchPoint엔티티가 아니라 request_points jsonb 안의 값 객체{x, y (0~1), text, refinedText?, useRefinedText}. 상태(해결/미해결) 없음 — 해결의 단위는 항목(결과 유무)과 회차다. 계획서·가이드에는 포인트가 없다. 대상 표시는 포인트가 하고, 주석 PNG 업로드 경로는 지웠다(#187 후속) — annotation_key 컬럼은 관리자 아티팩트 교체만 쓴다

회차 생명주기

한다회차는 부부가 연다 — 스튜디오 갤러리는 셀렉 제출과 N차 요청이 회차를 만들어 곧바로 REQUESTED 까지 올리고, 작가가 없는 개인 갤러리는 addPhotos 로 초안 회차를 만들어 요청문을 적은 뒤 내보내기가 제출한다. 작가가 결과를 다 올려 /send 하면 COMPLETED, 부부가 /confirm 하면 갤러리가 ARCHIVED. 계약 횟수(max_retouch_round_count)는 초안 생성과 제출 두 곳에서 검사한다.왜"보정 N회"는 계약 조건이라 회차가 세는 단위여야 하고, 한 번에 진행 중인 회차가 하나여야 작가가 무엇을 작업할지 분명하다. 셀렉 제출이 1회차를 함께 만드는 이유는 "제출했는데 보정 요청이 없는" 중간 상태를 없애기 위해서고, 확정이 갤러리를 보관으로 보내는 것은 보정 확정이 곧 납품 완료이기 때문이다.없으면부부가 회차를 여러 개 열어 두거나, 작가가 결과를 절반만 올리고 보내거나, 계약 횟수를 넘긴 요청이 들어온다.
addPhotos(개인):   최신 회차 REQUESTED → 409_1 ROUND_IN_PROGRESS · 횟수 소진 → 400_1 · 없거나 COMPLETED → DRAFTING(roundNo+1) 생성
셀렉 submit:       최신 회차 없거나 DRAFTING → RetouchRequestService.submit(roundNo, 선택 전부, requests) → 곧바로 REQUESTED
/rounds/{n}/requests: 최신 회차 REQUESTED → 409_3 · 횟수 소진 → 400_1 · 셀렉 밖 사진 → 400_17 → stage=RETOUCH → 알림 RETOUCH_REQUESTED(워크스페이스 멤버)
N차 /rounds/{n}/requests: 셀렉 SUBMITTED 전제(400_17 PHOTO_NOT_SELECTED), 셀렉 안 사진만
셀렉 withdraw(작가): 최신 회차 COMPLETED → 409 · REQUESTED ∧ 결과 있음 → 409 · 결과 없음 → reopenRequest() → DRAFTING
completeRound(/send): 항목 비었거나 결과 없는 항목 → 400_11 MISSING_RESULT → round.complete → stage=DELIVERY → 알림 RETOUCH_COMPLETED(갤러리 멤버)
confirm(부부):     최신 회차 COMPLETED → gallery.markRetouchConfirmed(now) (status CLOSED, stage ARCHIVED, archivedUntil) → 알림 RETOUCH_CONFIRMED

보정본 업로드 — S3 직접, 서명은 헐겁게

한다작가가 파일명 매칭으로 원본을 고르면 서버가 galleries/{g}/retouch/results/{n}/{uuid}.{ext} 키에 Content-Type 만 서명한 PUT URL 을 준다. 브라우저가 올린 뒤 complete 를 부르면 서버가 키 접두·중복을 검증하고 DB 락 밖에서 exists() 로 실제 업로드를 확인한 뒤 result_key 를 쓴다.왜원본 업로드와 같은 원칙(바이트가 서버를 지나지 않는다)이지만, 보정본은 작가가 툴에서 내보낸 파일이라 크기를 미리 알 수 없어 Content-Length·CRC 를 서명에 넣지 못한다. 그래서 서명은 헐겁고 대신 (1) 서버가 발급한 키 접두만 허용, (2) 완료 시 S3 HeadObject 로 존재 확인, (3) 같은 파일을 두 원본에 물리는 것 거절로 막는다. 보정본을 photos 행으로 만들지 않는 것은 분석 파이프라인(임베딩·점수·폴더)이 보정본을 다시 돌지 않게 하기 위해서다.없으면업로드 안 된 키가 결과로 저장돼 화면이 깨진 이미지를 보이거나, 작가가 임의 키에 쓰거나, 보정본이 임베더에 잡혀 분석 카운트가 어긋난다.입출력{files[{photoId, contentType}]} → {uploads[{photoId, resultKey, uploadUrl}], ttl} · {results[{photoId, resultKey, contentType}]} → 회차 상세
  • 허용 Content-Type: jpeg/png/webp/heic/heif → 확장자 매핑(UNSUPPORTED_CONTENT_TYPE 400_9). 키 접두 검증 validateResultKey(INVALID_RESULT_KEY 400_10). 업로드 미확인 RESULT_UPLOAD_INCOMPLETE 400_16. 같은 키 두 원본 DUPLICATE_RESULT 400_18.
  • 프론트는 체크섬 헤더를 붙이면 안 된다 — 서명에 없는 x-amz-* 헤더는 AccessDenied(RetouchWorkspace.tsx 주석).
  • 보정본으로 담기. 셀렉 SelectPhotosRequest.retouchPhotos[{photoId, retouchPhotoId}] → RetouchResultLoader.validateSelectable: 갤러리 소속 · 원본 일치 · 결과 존재 · 그 회차가 COMPLETED. 항목의 photo_id 는 원본, 화면은 resultUrl 이 있으면 보정본을 그린다. 현재 web 의 담기는 retouchPhotos: [] 고정(UI 미사용).

LLM 이 구체화하되 최종 선택은 사람이 하도록 refinedText 와 useRefinedText 를 나란히 둔다. LLM 이 꺼져 있으면 available=false 로 조용히 비활성.없으면작가와 부부가 요청 하나마다 메시지를 주고받는다.
