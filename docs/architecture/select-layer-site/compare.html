비교샷 셀렉 — 두 장 중 하나를 AI 가 고르고, 5초 안에 답한다

부부가 비교 뷰에서 나란히 놓인 두 장을 보며 "어느 쪽이 나아요?"를 누르면 동기 HTTP 로 판정이 온다. 서버가 분석 결과에서 사실(초점·백분위·연사·폴더)을 재고 미리보기 두 장과 함께 Sonnet 에 묻되, 8초 안에 답이 없거나 실패하면 템플릿 규칙(초점 ▸ 화질 ▸ 미학 ▸ a)으로 답한다. 판정은 셀렉 단위로 캐시돼 같은 쌍은 다시 묻지 않는다. 판정은 앨범을 바꾸지 않는다 — 담기는 사람이 누른다.

엔드포인트 · 검증 — AiCompareService

한다두 사진 id 를 받아 권한·같은 사진·같은 갤러리·분석 완료를 확인하고, 셀렉 행을 확보한 뒤 판정기에 넘겨 바로 판정을 돌려준다. @Transactional 이 없다 — 5초 안팎의 LLM 호출이 커넥션을 물면 안 된다.왜비교샷은 "지금 고민 중인 두 장"에 대한 즉답이라 잡·폴링 구조(추천)가 맞지 않는다. 사용자가 화면에서 기다리므로 동기여야 하고, 대신 예산(8초)을 넘기면 템플릿으로라도 반드시 답한다. 판정을 셀렉 단위로 저장·캐시하기 때문에 셀렉 행이 먼저 있어야 한다.없으면두 장을 고를 때마다 작가에게 묻거나, 답을 기다리다 화면이 멈추거나, 같은 쌍을 다시 물어 Bedrock 비용이 든다.입출력POST /api/v1/galleries/{g}/photo-selection/compare {photoA, photoB} → 200 {chosenPhotoId, confidence: clear|slight, reason, source: llm|template, cached}

사실 재기 — PairFactCollector · ComparablePhotoDto

한다두 사진의 분석 요약(백분위·선명도·클리핑·연사·피사체)과 폴더 이름·담김 여부에서 문장 목록과 facts JSON 을 만든다. 문장은 내부 라벨 a/b 로 쓴다.왜LLM 에게 사진만 주면 "상위 3%" 같은 숫자를 지어낸다. 서버가 잰 것만 문장으로 주고 프롬프트에서 "재료에 적힌 숫자만 쓴다"고 못 박아야 한다. 임계값(선명도 1.25배, 백분위 5p)은 "근거로 말할 만한 차이"의 하한이다. 템플릿 규칙도 같은 임계값을 써서 LLM 과 폴백의 판단 기준이 같다.없으면이유 문장이 사실과 어긋나고, 5p 미만의 미세한 차이가 "화질이 더 좋다"로 부풀려진다.

판정 — TemplateVerdictRule → LLM

한다템플릿 판정을 먼저 계산해 폴백으로 고정한 뒤, LLM 이 켜져 있으면 미리보기 두 장(긴 변 768)과 재료 문장으로 Sonnet 에 묻는다. 응답이 계약(chosen ∈ {a,b}, confidence ∈ {clear,slight}, reason 비어 있지 않음)을 지키면 LLM 답, 아니면 어떤 실패든 템플릿.왜사용자가 기다리는 동기 호출이라 "답이 없다"는 결과가 있어서는 안 된다. 그래서 폴백을 먼저 만들고 LLM 은 개선일 뿐이다. 재시도 0회·타임아웃 8초는 화면 예산이고, 사진을 실제로 본 답이 필요한 것(눈 감김·시선·흔들림은 수치에 없다)이 이미지를 보내는 이유다. 기권을 금지하고 slight 를 두는 것은 "거의 같아요, 굳이 고르면"이라는 톤을 위해서다.없으면Bedrock 장애가 곧 기능 장애가 되고, 수치가 같은 두 장에서 LLM 이 "못 고르겠다"고 답한다.
fallback = TemplateVerdictRule.decide(A, B)        // 초점 1.25배 ▸ 기술 백분위 5p ▸ 미학 백분위 5p ▸ a, confidence = "slight", source = "template"
if !llm.isEnabled: return fallback
try:
    imgA, imgB = PreviewImageReader.readJpeg(preview_key, 768) ×2     // 없으면 예외 → fallback
    out = llm.completeJson(system = ComparePrompt.SYSTEM,
                           parts = [text "두 장 중 어느 쪽을 담을지 골라 주세요.\n사진 a:", imgA, text "사진 b:", imgB, text "재료(측정된 사실):\n- …"],
                           schema = {chosen: a|b, confidence: clear|slight, reason}, maxTokens 1024, timeout 8s, maxRetries 0)
    if chosen ∈ SIDES ∧ confidence ∈ CONFIDENCES ∧ reason 비어 있지 않음: return Decision(…, reason.take(400), "llm")
    else warn("계약을 벗어남") → fallback
catch (any): warn("compare LLM 실패 → 템플릿 판정") → fallback

시스템 프롬프트 원문 (ComparePrompt.SYSTEM · PROMPT_VERSION compare-p2)

당신은 신랑신부 옆에 앉아 함께 사진을 고르는 베테랑 셀렉터다. 두 분이 사진 두 장을 놓고
고민하다가 당신에게 "어느 쪽이 나아요?"라고 물었다. 당신의 일은 **반드시 한 장을 고르고**,
왜 그 컷인지 두 분이 납득할 말로 설명하는 것이다.

규칙
- 반드시 a 또는 b 하나를 고른다. 기권은 없다. 두 장이 거의 같으면 confidence 를 "slight" 로
  하고 "거의 같아요, 굳이 고르면"의 톤으로 말한다. 차이가 분명하면 "clear".
- 판단 순서: ① 사진에서 직접 확인되는 차이 — 초점, 눈 감김, 시선, 표정, 흔들림, 잘림.
  ② 재료의 수치 — 백분위 차는 재료에 적힌 것만, 5포인트 이상일 때만 근거로 쓴다.
  ③ 흑백/컬러, 구도 취향, 분위기는 **취향**이다 — "이건 두 분이 정하실 몫"이라고 말하되,
  그래도 선택은 한다.
- 숫자·순위·장수는 재료에 적힌 것만 쓴다. 없는 숫자를 만들지 않는다.
- 말투: "~입니다/~요" 구어체, 부부에게 직접. 탈락한 쪽도 깎아내리지 않는다 — "저 컷도 좋지만"
  으로 시작해도 좋다. 모든 표현은 한국어로 쓴다.
- a/b 는 내부 라벨이다 — **문장에는 절대 쓰지 않는다.** 고른 쪽은 "이 컷", 다른 쪽은
  "다른 컷"이라고 부른다. 두 분 화면에는 a/b 표시가 없다.
- 길이: 2~4문장, 300자 안.

응답은 {chosen: "a"|"b", confidence: "clear"|"slight", reason} 하나다.

Bedrock 어댑터·설정(app.llm.*: compare-max-tokens 1024 · compare-timeout 8s · image-long-edge 768)은 AI 추천 문서의 Bedrock 어댑터 와 같은 클라이언트다. 소켓 타임아웃은 reasonsTimeout(3분)에 맞춰져 있고 요청 단위 apiCallTimeout 이 8초를 건다.

화면 (web)

  • 두 장을 직접 고르지 않는다. 비교 뷰(mode === "compare")에 떠 있는 인접 2장이 대상이고, compareCount === 2 일 때만 버튼이 산다(4장 보기: "AI 추천은 2장 보기에서 받을 수 있어요"). 부부 갤러리 gallery/page.tsx:433-508, 워크스페이스 GalleryWorkspace.tsx:538-593.
  • 캐시 키는 정렬한 id 쌍 — 서버의 순서 무관 계약과 같다. 쌍이 바뀌면 근거·오류가 함께 사라진다("다른 쌍의 근거가 남으면 거짓말").
  • 표시: "AI 추천 · 왼쪽/오른쪽 사진" + confidence 필(slight "거의 비슷해요" / clear "뚜렷한 차이") + reason. source === "template" 이면 "AI 응답이 늦어 사진을 직접 보는 대신 측정된 수치로만 고른 결과예요". 대기 문구 "사진을 직접 보고 판단해서 보통 5~6초 걸려요". 워크스페이스는 cached 를 "(저장된 판정)"으로 노출.
  • 버튼 가드: photo.preparing(409 사전 차단) · editLocked · caps.aiAssist = (personal || !manager) ∧ !archived ∧ windowOpen. 담기는 toggleCompareSelect 로 사람이 따로 누른다.
  • 오류 매핑(compare.ts:58-79): 400_1 · 404_3 · 409_7 · GALLERY_403_1/2/4 · GLOBAL_404_1. 502_1·503_1 매핑은 Lambda 실행기 시절의 잔재(서버는 502 를 흡수하고 503_1 은 추천 질의 코드).
