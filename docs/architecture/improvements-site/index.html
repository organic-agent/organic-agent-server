업로드 → AI 파이프라인은 어떻게 100분 넘게 끝을 못 보던 것이 7.5분이 됐고, 그게 얼마인가

7,189장 갤러리 하나를 올리고 AI 폴더가 만들어지기까지 100분이 넘도록 끝을 보지 못하던 것(업로드 63.5분 + 분석 40분 이상 미완주)이 약 7.5분이 됐습니다. 세 시대를 거쳤습니다 — 단계당 Lambda 하나가 15분 데드라인에 걸려 자기를 다시 부르던 v1, 조정자 Lambda가 샤드 N개를 동시에 띄우던 샤딩(중간 단계, 지금은 삭제), 그리고 wes 스윕이 50장 배치를 배정하고 점수는 EC2 GPU 워커가 직접 집어 가는 v2(현재). 이 사이트는 각 단계가 무엇을 고쳤고 실측이 어땠는지, 그리고 지금 구조로 운영하면 갤러리 하나·추천 한 번·한 달에 얼마가 드는지를 정리합니다.

세 시대 — 무엇이 바뀌었나

시대시기구조7,189장 갤러리 (업로드 + 분석)

먼저 잡아야 할 사실 하나. "람다 샤딩"은 중간 단계였고 지금 코드에는 없다(AI repo #99·#101 삭제, CLAUDE.md:55 "체인·샤딩·자기 재호출은 없다"). 이 사이트에서는 이력으로만 쓰고, 현재 구조는 wes EmbedDispatcher + GPU 워커 pull + categorize 1회다.
그리고 숫자 하나. 자주 인용되는 77.5분은 v1이 아니라 「원본 업로드 63.5 + 32 샤드 분석 14.0」이다(upload-timing §7.3 표의 왼쪽 열). v1 직렬은 분석이 40분을 넘겨도 끝나지 않아 확정값이 없다. 그래서 기여는 갈라 적는다 — 샤딩: 분석 40분+ 미완주 → 14분 한 라운드, 2048 리사이즈: 업로드 63.5 → 4.6분.

시대별 흐름도 — 같은 세 단계를 누가 어떻게 돌리는가

실선 = 호출·쓰기, 점선 = 읽기·관측. v1·샤딩은 Lambda가 Lambda를 부르는 화살표가 있고, v2에는 그 화살표가 없다 — 단계 사이는 전부 DB 행을 wes가 관측해서 잇는다.

읽을 때 주의

  1. 샤딩은 현재 코드에 없다. 개선 이력으로 읽되, 현재 구조는 wes EmbedDispatcher + GPU 워커 pull + categorize Lambda 1회다(pipeline-v2-site).
  2. 2048 리사이즈와 GPU 점수는 영향 범위가 다르다. 리사이즈는 업로드·embedder를, GPU는 score만 빠르게 했다. score는 embedder가 만든 1024px 미리보기만 읽으므로 마스터 크기와 무관하다.
  3. 77.5분은 v1 값이 아니다. 「원본 업로드 63.5 + 32 샤드 분석 14.0」의 조합이다. v1 직렬 합계는 100분+ 미완주로 쓰고, 4.2×(77.5 → 18.3)의 거의 전부는 2048 리사이즈 몫이다.
  4. 비용 수치는 장수 기준이 둘이다. 822장 기준(score-speedup §5)과 7,189장 기준(upload-timing, score-lambda-vs-gpu). 표마다 장수를 적었다.
  5. 인프라 쪽 GPU 개선 문서(infra PR #64)는 아직 열려 있다. 브랜치 docs/63-lambda-to-gpu-improvement, 커밋 fa4795b. 여기서는 그 브랜치를 읽어 인용했다.
  6. categorize #108은 "메커니즘 + 1차 실측(개선 없음) + 09-10 재측정 예정"이다. 1차 실측은 회선 변동(업로드 평균 46Mbps, 평소 61)이 겹쳐 체인 합계 8분 21초는 대표값이 아니다. categorize 자체 수치(70초)는 유효하다.
  7. 09-09 체인 실측에서 확정된 것 하나: GPU 워커 자기 정지(AI #107) 작동 확인 — score 끝 30초 뒤 워커가 스스로 stop 요청을 냈다.
