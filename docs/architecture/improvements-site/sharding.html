Lambda 하나가 15분에 걸리자, Lambda가 Lambda를 32개 띄우게 했다

v1은 단계당 Lambda 하나가 갤러리를 통째로 처리했고, 7,189장은 업로드 63.5분 뒤 분석이 40분을 넘겨도 끝나지 않았습니다(합계 100분+, 확정값 없음). score Lambda(8GB ≈ 5 vCPU)가 장당 1.5초라 822장도 512장에서 15분 데드라인에 닿았고, 7,183장은 자기 재호출을 반복하며 40분을 넘겼습니다. 샤딩은 그 Lambda를 조정자 하나 + 샤드 N개로 바꿔 벽시계를 1/2.3~1/4로 줄였습니다. 대신 GB-초 비용은 그대로였고, vCPU 상한·RDS 커넥션·호스트 편차라는 세 벽에 부딪혀 이틀 뒤 GPU 워커(v2)로 대체됐습니다.

원인은 단순했다. score Lambda 8GB(≈5 vCPU)에서 장당 1.5초이니 512장에 데드라인이 온다. 한 호출의 시간은 다운로드 40s + 모델 로드 16s + 사진 512장 779s. 15분 앞에서 스스로 멈추고 같은 페이로드로 자기를 다시 부르는 구조라, 7천 장은 재호출이 여러 번 이어지며 40분을 넘겼다.

개선 — 조정자 하나 + 샤드 N개

  1. 디스패처는 SQS·Step Functions가 아니라 Lambda 자신. wes가 보낸 EVENT를 받은 함수가 조정자가 되어 0.7초 만에 샤드 N개를 EVENT로 띄운다. N = clamp(ceil(n / SHARD_PHOTOS), 1, MAX_SHARDS).
  2. 샤드는 position % total로 사진을 나눠 갖는다. 같은 갤러리의 같은 샤드가 두 번 돌지 않도록 advisory lock 키 (gallery × 64 + shard).
  3. 손잡이 둘. SHARD_PHOTOS 250 → 150(#60/#61), MAX_SHARDS 8 → 32(#64/#65). 환경변수.
  4. Lambda 설정. embedder 3GB / 예약 동시성 32, score 8GB / 임시 저장소 10GB / 32, categorize 3GB / 2. 타임아웃 900s.
  5. 동시성 32의 근거는 RDS. db.t4g.micro max_connections 79, 평상시 24 + 샤드 32 = 56. ALTER ROLE embedder CONNECTION LIMIT 32.
  6. 15분 데드라인은 여전히 있었다. 같은 샤드로 자기 재호출(STOP_MARGIN_SECONDS). 샤딩은 데드라인을 없앤 게 아니라 데드라인 안에 끝나게 잘게 쪼갠 것이다.
  7. 마지막 샤드가 다음 단계를 부른다. score 샤드가 끝날 때 result.scoreShards.done을 올리고, N/N에 닿은 샤드가 wes-categorize를 EVENT로 부른다.

샤딩이 부딪힌 세 벽 — 다음 단계의 동기

vCPU 연산 상한
Lambda 10GB가 ≈6 vCPU. CLIP 0.68s + ARNIQA 0.80s는 CPU에서 더 줄지 않는다. ARNIQA 입력 해상도를 낮추면 Spearman 0.638/0.536/0.479(896/768/640px)로 무너져 폐기(score-speedup §4.4).
RDS 커넥션
샤드 32 = 커넥션 61/79. 샤드를 더 늘리면 앱 커넥션을 먹는다. 동시성 상한이 곧 처리량 상한.
호스트 편차 1.7×
느린 Lambda 호스트(장당 2.39s)를 만난 샤드가 꼬리를 +3.5분 끈다. 32개를 동시에 띄우면 그중 하나는 꼭 느리다.
