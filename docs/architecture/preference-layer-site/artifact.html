산출물 — 모델 파일이 아니라 숫자 1,548개짜리 행 하나

이 층이 만드는 것은 ML 모델 파일도, 점수 하나도 아니다. 로지스틱 회귀의 가중치 벡터 한 행이다. 은닉층·비선형이 없으니 추론에 모델 런타임이 필요 없고, wes 는 사진 한 장의 특징 x(1,547개)와 내적 한 번으로 pref 점수를 얻는다. 그래서 행이 RDS 테이블 한 줄에 들어가고, 무엇으로 배웠고 얼마나 나아졌는지까지 같은 행에 남는다.

가중치 벡터 한 행

한다사진의 특징 1,547개에 곱할 가중치와 절편, 그리고 prior 와 섞을 비중 λ 를 한 행으로 묶는다. PreferenceModel.to_row() 가 그대로 preference_models 의 컬럼이 된다.왜선형 모델이라 가중치가 곧 모델이다. 파일·S3·런타임을 두면 "어느 파일이 지금 것인가"를 따로 관리해야 하는데, 행 하나에 버전 키·학습 재료·홀드아웃 성적·active 를 함께 두면 테이블 자체가 이력이 된다.없으면wes 가 모델 서빙 런타임을 들이거나 Lambda 를 사진마다 불러야 한다. 이 서비스의 원칙(사진당 호출 없음)에 어긋난다.입출력train() → PreferenceModel → to_row() → INSERT. 역방향 from_row() 는 CLI·테스트용

특징 x — 자리 순서가 계약이다 (pref-v1)

한다사진 한 장을 숫자 1,547개로 만든다. 전부 DB 에 이미 있는 값이고 새 모델 호출은 없다.왜학습기(Python)와 추론(wes, Kotlin)이 다른 코드라 자리 순서가 어긋나면 내적이 조용히 엉뚱한 값을 낸다. 그래서 순서를 FEATURE_SPEC = "pref-v1" 이름으로 못 박고 행에 함께 저장한다. 계약이 바뀌면 이름을 올린다.없으면가중치는 맞는데 특징 자리가 밀린 채로 점수가 나오는, 티 나지 않는 오류가 생긴다.입출력GalleryData(갤러리 전체 행) → Features{scalar (n,11), emb (n,1536), emb_mean (1536,)}

왜 갤러리 평균을 빼나

촬영 장소·작가 스타일은 갤러리마다 다르다. 임베딩의 절대 위치를 배우면 "이 스튜디오 사진이 좋다"를 배우게 되고 다른 갤러리에 옮겨지지 않는다. 평균을 빼면 "그 갤러리 안에서 어느 쪽이 선택되는가"를 배운다. 추론하는 wes 도 같은 갤러리의 분석 완료 사진 전체로 평균을 다시 구해 빼야 한다 — 학습 때의 평균을 저장해 쓰는 게 아니다(Features.emb_mean 은 확인용).
