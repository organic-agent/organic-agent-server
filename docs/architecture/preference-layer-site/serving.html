서비스 연결 — 사진 한 장과 벡터가 만나는 지점

이 페이지는 wes 에 앞으로 붙을 코드의 자리를 설명한다. 지금 추천 잡(AiSelectionJobRunner.plan)은 score = z(prior) [+ 균형·유형 항] 으로 순위를 매기고 폴더 쿼터·MMR 로 고른다(이웃 문서). 선호 층은 그 식에 항 하나 — λ·z(pref) — 를 더할 뿐이다. 추천이다 아니다를 가르는 문턱값은 없고, 몇 장을 어디서 고르느냐는 지금 있는 쿼터와 MMR 이 정한다. 그리고 갤러리가 CLOSED 될 때 Lambda 를 한 번 부른다.

현재 코드에서 확인한 사실 (2026-09-09, wes main@1503a9a)
RecommendationScoring.combine 에 pref 항이 없다 · 러너의 loadEmbeddings 는 DINOv3(embedding)만, 그것도 범위 폴더 사진만 읽는다 · GalleryService.close() 는 상태만 바꾸고 아무것도 부르지 않는다 · preference_models 를 읽는 Repository 가 없다. 아래는 전부 설계이며, 붙이는 순서와 남은 일은 6.

추천 잡 안에서 — pref 항이 들어가는 자리

prior 는 어디서 만들고 어디서 쓰나

재료는 배치가 DB 에 적고, prior 자체는 추천 잡이 매번 메모리에서 만든다. 선호 층도 같은 모양이다 — 가중치 행은 DB 에, pref 점수는 추천 잡이 그 자리에서 내적으로.

단계하는 일놓이는 곳
score (GPU 워커 · Lambda)ARNIQA(spaq) 기술 점수, CLIP+LAION 미학 점수 — 사진 한 장의 절대 점수. CLIP 임베딩·피사체·연사 클러스터도 여기photo_analysis.sub_scores · clip_embedding · subjects · cluster_id
categorize (Lambda)갤러리 안에서 두 점수를 백분위(0~100)로. 컨셉 그룹technical_pct · aesthetic_pct · embed_group_id
wes AiSelectionJobRunner.plan추천 잡이 돌 때 메모리에서 0.5·tech + 0.5·aes → z → (담은 사진 5장 이상이면 deficit·lift 항) → 쿼터·MMR. prior_z 는 근거 문장 재료로도DB 에 없음
목표 같은 자리active 행을 읽어 사진마다 내적 → z → λ·z(pref) 항 추가. score_breakdown 에 pref_z 남김DB 에 없음 (행만 있음)

내적 → pref → 융합

한다사진마다 "이 사진이 다른 부부들이 고른 방향과 얼마나 닮았나"를 뜻하는 실수 하나를 만들고, prior 와 각각 갤러리 안에서 z 정규화한 뒤 λ 로 비중을 정해 더한다.왜prior(백분위 평균)와 pref(로짓)는 단위가 다르다. z 로 맞추면 λ 가 "prior 한 표준편차 대비 pref 몇 표준편차"라는 뜻이 된다. 문턱값을 두지 않는 이유는 이 층이 배운 것이 부부 평균이라 개별 사진을 잘라낼 근거가 되지 못하기 때문이다 — 순위만 옮긴다.없으면prior 만으로는 부부가 고른 장면의 절반이 후보 90 밖이다(갤러리 8 실측 recall 0.5).입출력행 {w_scalar, w_emb, bias, lambda} + 갤러리 사진 전체 → score[]
pref(p)  = w_scalar · x_scalar(p) + w_emb · x_emb(p) + bias            x_emb 는 갤러리 평균을 뺀 것
score(p) = z(prior(p)) + λ · z(pref(p))  [+ W_BALANCE·z(deficit) + W_PREF·z(lift)]      prior = 0.5·technical_pct + 0.5·aesthetic_pct
λ        = preference_models.lambda = n / (n + n₀)      active 행 없음 → λ 항 없음 → 지금 점수 그대로

예. 기술 40 · 미학 70 · 커플 컷이면 prior 55. 임베딩이 "베일을 든 신부 클로즈업" 방향이고 w_emb 가 그 방향을 양수로 배웠다면 pref 가 큰 양수. z 를 취해 prior +0.3, pref +1.8, λ 0.5 이면 score 1.2 — prior 만으로는 중간이던 사진이 폴더 안 상위로 올라간다. 반대 방향이면 조금 내려간다. 어느 쪽이든 잘라내지 않으므로 후보에서 사라지지는 않는다. 그 뒤는 지금 코드 그대로 — FolderQuota 가 폴더별 장수를 정하고 MmrSelector 가 연사 클러스터당 최고점 1장만 남기고 MMR 로 고른다.

wes 에 붙을 코드 — 2단계 안

// 1. active 행 — embedding_model · model_version 이 이 갤러리의 photo_analysis 와 같고 feature_spec 이 pref-v1 인 것. 없으면 아래 전부 건너뜀
val model = preferenceModelRepository.findActive(embeddingModel, modelVersion, FEATURE_SPEC) ?: return combinedAsIs

// 2. 특징 조립 + 내적 (갤러리 평균을 먼저 구한다 — 범위 폴더가 아니라 분석 완료 사진 전체로)
val mean = meanOf(rows) { concat(l2(it.embedding), l2(it.clipEmbedding)) }
val pref = DoubleArray(n) { i ->
    val xs = scalars(rows[i], groupSize, clusterSize, order)          // 11, pref-v1 순서 (artifact.html#features)
    val xe = concat(l2(rows[i].embedding), l2(rows[i].clipEmbedding)) - mean
    dot(model.wScalar, xs) + dot(model.wEmb, xe) + model.bias
}

// 3. RecommendationScoring.combine 에 항 하나
val score = z(priorRaw) + model.lambda * z(pref) /* + 기존 deficit · lift */

이름 충돌 주의 — 지금 코드의 "pref" 는 다른 것이다
RecommendationScoring.W_PREF · 러너의 prefOn · 잡 result.preferenceOn 은 이 세션의 부부가 담은 사진의 피사체 유형 lift(in-session affinity)를 뜻한다. 담은 사진이 5장 이상이고 subjects 가 있을 때만 켜지는 항이다. 선호 가중치 층은 다른 부부들에게서 배운 평균이며 별개다. 붙일 때 이름을 가르는 것이 좋다 — 예: 기존 항은 affinity, 이 층은 learnedPref. 부부별 편차는 기존 in-session 항이, 평균 취향은 이 층이 맡는 분업이다.

트리거 — 갤러리가 CLOSED 될 때

한다GalleryService.close()(또는 보정 확정 markRetouchConfirmed)로 갤러리가 CLOSED 가 되면 커밋 뒤 preference Lambda 를 EVENT 로 부른다. 페이로드 {"galleryId": N}.왜라벨(최종 선택)이 확정되는 시점이 마감이다. 학습은 어차피 마감 갤러리 전부를 다시 모으므로 galleryId 는 로그용이고, 호출을 놓쳐도 다음 마감에서 따라잡는다. 응답을 기다리지 않는다(EVENT) — 학습이 갤러리 마감을 막으면 안 된다.없으면수동 CLI 로만 학습된다(지금 상태).입출력CLOSED 전이 → StageInvoker 와 같은 모양의 포트 → Lambda EVENT. 결과는 preference_models 행으로만 관측
선택지장점단점
A. CLOSED 전이 훅 (기본 설계)마감 직후 최신 행. 분석 파이프라인의 StageInvoker(EVENT · 로컬은 LocalProcessStageInvoker) 패턴을 그대로 쓴다wes 에 포트·설정·로컬 대역 스크립트(scripts/lambda/preference.sh)가 필요. 재오픈 → 재마감이면 두 번 돈다(무해 — 같은 결과)
B. EventBridge 하루 1회 스케줄wes 코드 변경 없음. 새 마감이 없으면 같은 결과를 다시 쓸 뿐최대 하루 지연. 행이 매일 하나씩 쌓인다(이력 표로는 오히려 장점)

마감 즉시일 필요는 없다. B 로 시작해 A 를 나중에 붙여도 된다 — 결정은 6. 열린 결정.
