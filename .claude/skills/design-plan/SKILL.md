# 설계 계획 (요구사항 → 유형 → 이슈 → 단계별 결정 → 구현 → PR)

입력: $ARGUMENTS — 요구사항 한 줄(예: "analysis 로직이 복잡해서 리팩토링", "galleries에 필드 추가", "5명이 7,000장씩 동시에 올려도 버티게").
비어 있으면 **Phase R(이어 하기)** 로 간다.

이 스킬의 규칙은 아래 참조 파일이 정한다. 시작할 때 넷을 Read로 읽어라.

- `reference/glossary.md` — 강의 두 편(아키텍처 용어 8가지 · W²HO)의 용어 뜻과 이 하네스에서 쓰이는 자리. 문서·질문에 쓰는 말은 여기 정의를 따른다

- `reference/types.md` — 무게 질문 셋, 유형 9개, 태그 5개, 30초 판별 트리, 갈아타기, 유형 → 커밋 타입
- `reference/stages.md` — 유형별 단계 목록, 단계마다 물을 것·남길 것·관문, 태그가 더하는 단계
- `reference/doc-templates.md` — 계획 문서 모양(한 파일 / 폴더), 상태 머리말, 단계 칸 모양

## 질문하는 방식 (모든 Phase 공통)

- **한 번에 질문 하나.** 추천 답을 먼저, 이유 한 줄과 함께. 고를 수 있는 질문은 AskUserQuestion(추천을 첫 옵션, "(Recommended)")으로, 열린 질문은 글로.
- **코드·문서로 답할 수 있는 건 묻지 않는다.** 먼저 Grep·Read로 찾아보고, 찾은 사실을 근거로 추천을 만든다.
- 사용자가 "알아서 해"·"추천대로"라고 하면 추천으로 정하고 문서에 "(추천대로)"라고 남긴다.
- 답이 모호하면 W²HO 순서로 되묻는다 — 왜(어디가 불편한가, 숫자는?) → 무엇(무엇이 필요한가) → 어떻게 → 판단.
- 한 단계의 질문이 끝나면 그 단계 칸을 문서에 쓰고, **3줄 요약**을 보여 준 뒤 "확정하고 다음 단계로 갈까요?"를 묻는다. 확정되면 칸에 `확정 YYYY-MM-DD`를 붙이고 머리말 상태를 갱신한다.

## Phase 1: 구체화

1. 요구사항에서 **누가 · 무엇을 못 하나/무엇이 불편한가 · 어디까지** 를 뽑는다. 빠진 것만 묻는다.
2. 관련 코드를 먼저 찾아본다(도메인 폴더, 엔티티, 컨트롤러, 마이그레이션). 찾은 위치를 다음 Phase의 근거로 쓴다.

> 다음 Phase 조건: 요구가 "누가 · 무엇 · 범위" 한 문단으로 정리됐을 때

## Phase 2: 라우팅 (유형 고르기)

1. `reference/types.md`의 **30초 판별 트리**를 따라 유형을 고르고, **태그**를 붙인다.
2. **무게 질문 셋**(되돌리기 비용 · 영향 범위 · 불확실성)에 각각 낮음/중간/높음과 근거 한 줄을 단다.
3. 사용자에게 보여 준다:
   ```
   유형: B3 복잡한 기능 추가 · 태그: +스키마 +계약
   무게: 되돌리기 높음(테이블 추가) · 범위 중간(gallery·photo) · 불확실성 중간(데이터 모델 2안)
   타는 단계: 요구 → 드라이버 → 대안 → 결정 → (ADR: 데이터 모델) → API 계약 → 마이그레이션 계획 → 구현 계획
   건너뛰는 것: 기준선 측정(성능 요구 없음)
   문서: docs/plans/<오늘>/<이름>.md 한 파일
   ```
4. 사용자 확인을 받는다. 다른 유형을 말하면 그대로 따르되, 무게 질문과 어긋나면 한 번만 이유를 말한다.
5. **S2(실험)가 먼저 필요하면**("재 봐야 안다") 그것부터 하자고 제안한다.

> 다음 Phase 조건: 유형·태그를 사용자가 확인했을 때

## Phase 3: 이슈

1. `open-issue` 스킬을 호출한다. 인자로 Phase 1·2 결과를 넘긴다: 종류(커밋 타입, `reference/types.md` 매핑), 제목, Why 2~3줄, 작업 항목, 연관 도메인, **작업 유형 줄**(`작업 유형: B3 +스키마 +계약`).
   open-issue는 이 입력이 있으면 자기 구체화 Phase를 건너뛴다.
2. **B1도 이슈를 따로 연다**(2026-10-08 결정). 본문 맨 아래 `작업 유형: B1` 줄이 있어 나중에 `gh issue list --search "작업 유형: B1"`로 모아 묶을 수 있다.
3. 이슈 번호·브랜치를 받아 둔다.

> 다음 Phase 조건: 이슈 번호와 브랜치가 생겼을 때

## Phase 4: 계획 문서 만들기

1. `reference/doc-templates.md`대로 만든다.
   - **B1**: 계획 문서 없음 → Phase 6으로.
   - **B2·B3·B4·B6·S1·S2**: `docs/plans/<오늘 YYYY-MM-DD>/<이름>.md` 한 파일.
   - **B5·B7**: `docs/plans/<오늘>/<이름>/` 폴더(README · 01 · 02 · 03 · adr/). 템플릿은 `docs/design-method/templates/`에 있으면 복사하고, 없으면 `reference/doc-templates.md`의 모양으로 쓴다.
   - S2 결과는 `docs/experiments/`에, S1 회고는 `docs/improvements/<오늘>/`에 쓴다(계획 파일은 진행용).
2. 머리말에 유형·태그·이슈·브랜치·상태(`단계 0/N`)와 **단계 목록**을 적는다. 단계 목록은 `reference/stages.md`의 그 유형 단계 + 태그가 더하는 단계다.
3. 여러 날 걸릴 B5·B7은 그날 할 일을 `docs/plans/<오늘>/<이름>-day.md`(오늘 일기)로 따로 둔다 — 폴더는 계속 고쳐 쓰는 지식, 오늘 일기는 그날의 목표·순서·하지 않는 것·기록.

## Phase 5: 단계 반복 (계획 확정까지)

단계 목록을 위에서부터 하나씩:

1. `reference/stages.md`에서 그 단계의 **물을 것 · 남길 것 · 관문**을 읽는다.
2. 코드·기존 문서·측정 결과를 조사한다. 조사로 답이 나오는 것은 사실로 적는다.
3. 질문 방식대로 하나씩 묻고 결정을 받는다.
4. 문서의 그 단계 칸을 채우고(W²HO 순서), 3줄 요약 → 확정 → 상태 갱신.
5. **갈아타기**: 진행 중에 `reference/types.md`의 갈아타기 신호가 보이면 멈추고 알린다 — "B2로 시작했는데 새 테이블이 필요합니다. B3(+스키마)로 올릴까요?" 동의하면 머리말 유형과 남은 단계 목록을 고치고 이슈에 한 줄 코멘트(`gh issue comment`)를 남긴다.
6. **측정이 필요한 단계**(B7 기준선, S2)는 `.claude/rules/load-test.md`를 따른다 — 회차 명령을 주고 사용자가 실행한다. 결과를 받으면 해석해 칸에 적는다.

> 다음 Phase 조건: 마지막 계획 단계("구현 계획")가 확정됐을 때. 머리말 상태를 `계획 확정 · 구현 중`으로.

## Phase 6: 구현

1. 구현 계획 칸(파일·순서·PR 쪼개기)대로 구현한다. `.claude/rules/*`가 경로별로 적용된다.
2. 테스트: 유형의 **관문**(`reference/stages.md`)을 만족시킨다 — B2·B3 통합 테스트, B4·B5 고정해 둔 테스트, B6 재현 테스트, B7 같은 스크립트로 재측정(사용자 실행). 필요하면 `write-test` 스킬.
3. `./gradlew test`(또는 관련 테스트) 결과를 그대로 보고한다. 실패를 숨기지 않는다.
4. 커밋·푸시는 사용자 확인 뒤 `commit-push` 스킬로.
5. PR이 여러 개로 쪼개진 계획이면 PR 단위로 6~7을 반복하고 문서의 구현 계획 표에 PR 번호를 적는다.

> 다음 Phase 조건: 관문을 통과했고 푸시됐을 때

## Phase 7: PR

1. `open-pr` 스킬을 호출한다. 계획 문서 경로를 함께 넘겨, PR "판단" 칸을 계획 문서의 결정·트레이드오프·남긴 것에서 채우게 한다.
2. 머리말 상태를 `PR #N`으로.

## Phase 8: 설명 자료 (조건부)

- **B3·B5·B7 또는 +레포 간**이면 묻는다: "설명 자료를 만들까요? (그림 위주 HTML 페이지 / 짧은 md)" — 2026-10-08 결정.
- HTML이면 Artifact로 그림 위주(W²HO 순서, 결정과 트레이드오프가 한눈에) 페이지를 만들고, md면 `docs/plans/…/<이름>-explained.md`에 한 화면 분량으로.
- 그 밖의 유형은 사용자가 요청할 때만.
- 끝나면 머리말 상태를 `완료`로.

## Phase R: 이어 하기 ($ARGUMENTS가 비었을 때)

1. 현재 브랜치에서 이슈 번호를 뽑고(`{type}/{번호}-…`), `docs/plans/` 아래에서 머리말에 그 이슈 번호가 있는 계획 문서를 찾는다(`grep -rl "이슈: #<번호>" docs/plans`).
   못 찾으면 상태가 `완료`가 아닌 가장 최근 계획 문서들을 보여 주고 고르게 한다.
2. 머리말의 유형·상태·단계 목록을 읽고 "B7 · 단계 3/7(대안) 진행 중 — 이어 갈까요?"를 묻는다.
3. 그 Phase로 돌아간다. B5·B7이면 오늘 일기(`<이름>-day.md`)가 오늘 날짜 폴더에 없을 때 만들지 묻는다.
