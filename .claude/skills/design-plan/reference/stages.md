# 유형별 단계

> 단계 = 계획 문서의 칸 하나. 단계마다 **물을 것**(사용자 결정이 필요한 것) · **남길 것**(문서 칸) · **관문**(확정 조건).
> 조사로 답이 나오는 것은 묻지 않고 사실로 적는다. W²HO: 왜 → 무엇 → 어떻게 → 판단. 용어(드라이버·택틱·패턴·트레이드오프·ADR …)는 [glossary.md](glossary.md).

| B3 | ● | ● | — | ● | ● | ● | △ | 시나리오 통합 테스트 + 웹 연동 확인 |

## 단계 목록

### B1 간단한 수정
계획 문서 없음. 라우팅 확인 → 이슈 → 구현 → PR. PR 판단 칸은 "—" 또는 한 줄.

### B2 간단한 기능 추가
1. **요구** — 물을 것: 누가, 무엇을, 응답에 무엇이 필요한가 · 남길 것: Why 2줄, 된다/안 된다 체크박스 · 관문: 체크박스가 테스트로 옮길 수 있는 문장
2. **구조 확인** — 조사: 어느 도메인·레이어(controller·service·repository), 비슷한 기존 API · 물을 것: 권한(누가 호출 가능), 없을 때 응답 · 남길 것: "구조 안 바꿈" 근거 한 줄, 따를 기존 코드 경로 · 관문: 새 테이블·새 도메인이 없다(있으면 B3로 갈아타기)
3. **구현 계획** — 남길 것: 바꿀 파일 표, 테스트 시나리오(성공·권한·없음) · 관문: 사용자 확정

### B3 복잡한 기능 추가
1. **요구** — 비즈니스 원문 + 설계 언어로 옮긴 것, 기능 목록
2. **드라이버** — 물을 것: 구조를 바꾸는 요구는 무엇인가, 품질 속성(권한·데이터 양·동시성·응답 시간)이 있으면 숫자, 제약 · 남길 것: 요구 분류표(기능/품질/제약 · 드라이버 O/X) · 관문: 품질 속성마다 숫자나 "협의 필요"
3. **대안** — 조사: 기존 도메인 경계, 비슷한 기능 · 물을 것: 도메인 경계·데이터 모델 2안 이상(+"새로 안 만들고 기존 것 확장") · 남길 것: 대안 표
4. **트레이드오프·결정** — 남길 것: 드라이버 품질 속성 전부를 열로 한 비교표, 결정 문장 "우리 상황에서는 X를 고른다. A를 얻고 B는 감수한다" · 관문: 사용자 확정
5. **ADR(△)** — 되돌리기 어려운 결정(테이블 구조·도메인 경계)만, 같은 파일의 "결정 기록" 칸에
6. **구현 계획** — 남길 것: PR 쪼개기 표(순서·범위·관문), 테스트 시나리오 · 관문: 사용자 확정

### B4 리팩터링 — 국소
1. **요구** — 무엇이 읽기·고치기 어렵나 한 줄
2. **동작 고정** — 조사: 대상 코드를 지키는 기존 테스트 · 물을 것: 모자란 경로를 보강할지 · 남길 것: 지키는 테스트 목록 · 관문: 바꿀 코드의 진입점이 테스트로 덮였다(모자라면 `qa-domain` 일부)
3. **변경 목록** — 남길 것: 전 → 후 표, "동작은 그대로" · 관문: 응답·스키마 변경 없음(있으면 갈아타기)

### B5 리팩터링 — 구조 (폴더)
1. **요구** (`01`) — 왜 구조가 문제인가: 변경 비용(한 기능 추가에 손대는 파일 수)·버그 빈도 같은 숫자나 사례
2. **드라이버** (`01`) — 변경 용이성 품질 속성을 측정 가능한 문장으로("단계 하나 추가에 파일 N개 이하")
3. **기준선** (`02`) — `qa-domain` 스킬로 특성화 테스트 · 관문: 진입점 전부 덮임
4. **대안** (`03`) — `refactor-domain` 진단 findings를 근거로 구조 2~3안
5. **트레이드오프·결정 → ADR** (`03`, `adr/`)
6. **구현 계획** — 작은 단계 PR 표(각 단계 뒤 특성화 테스트 통과) · 적용은 `refactor-domain`

### B6 버그 수정
1. **증상·재현** — 물을 것/조사: 언제·누구에게·어떤 입력에서, 로그(갤러리·잡 번호) · 남길 것: 재현 순서
2. **원인** — 조사: 코드·로그·DB · 남길 것: 원인 후보 → 확정 원인 한 줄 · 관문: 원인이 코드 위치로 특정됨
3. **재현 테스트** — 남길 것: 실패하는 테스트(운영에서만 재현되면 로그·DB 쿼리로 대신하고 그렇게 적는다)
4. **수정 계획** — 물을 것: 국소 수정으로 충분한가(구조 원인이면 B5·B7 이슈 제안) · 남길 것: 고칠 곳, 재발 방지 한 줄

### B7 성능·용량 개선 (폴더)
1. **드라이버** (`01`) — 비즈니스 원문 → 품질 속성 시나리오(자극원·자극·환경·대상·응답·측정 숫자), 제약, 가설 · 관문: 측정 칸이 모두 숫자
2. **기준선** (`02`) — 재현 방법(스크립트)·측정 정의·회차 · 측정은 `.claude/rules/load-test.md`대로 사용자가 실행 · 관문: 지금 값이 숫자로, 가설 판정
3. **대안** (`03`) — 시나리오마다 택틱(무엇을) → 패턴(어떤 구조로), "아무것도 안 함" 포함, 해결 순서(코드·DB → 새 기술 → 증설)
4. **트레이드오프·결정 → ADR** (`03`, `adr/`)
5. **구현 계획** — PR 표, 배포 순서, 재측정 계획
6. **검증** — 같은 스크립트로 후 측정 → `docs/improvements/<날짜>/`
여러 날이면 그날 일은 오늘 일기(`<이름>-day.md`)에.

### S1 장애 대응
1. **증상** — 영향 범위·시작 시각 · 복구가 먼저, 질문은 최소
2. **고침** — hotfix 브랜치(main), 최소 수정, 배포 확인
3. **회고** (`docs/improvements/<날짜>/`) — 증상 · 원인 · 고친 것 · 재발 방지 · 재발 방지가 구조면 새 `/design-plan` 제안

### S2 실험
1. **질문·가설** — 무엇을 알면 결정할 수 있나, 판정 기준 숫자
2. **방법** — 데이터·환경·스크립트·회차
3. **실행·결과** — 측정은 사용자가 실행(load-test 규칙)
4. **결론** (`docs/experiments/`) — 가설 판정, 다음 결정에 줄 것 · 결론이 "바꾸자"면 새 `/design-plan`

## PR "판단" 칸에 넣을 것 (Phase 7)

계획 문서에서 가져온다: 고른 것과 버린 대안 한 줄 · 감수한 트레이드오프 · 남긴 것·다음 할 일 · (B7) 재검토 조건.
B1·B2·B4는 1줄이면 충분하다.
