# 용어집 — 이 하네스가 쓰는 강의 용어

> 두 강의를 이 저장소의 말로 요약한 것이다(원문 옮김 아님). 정의는 짧게, **이 하네스의 어디서 쓰이나**를 함께 적는다.
> - 강의 A: "AI 시대, 개발자가 알아야 할 아키텍처 용어 8가지" — https://www.youtube.com/watch?v=5dlKBmlMEKE — **무엇을 생각하나**
> - 강의 B: "기술이 아니라 논리로 설득하라 — W²HO 프레임워크"(코딩하는기술사) — https://www.youtube.com/watch?v=F5EMgGQhnS4 — **어떤 순서로 꺼내나**
> 시각(mm:ss)은 강의의 그 장면. 더 긴 개인 정리는 작성자 로컬 `docs/design-method/`(gitignore)에 있다.

## A. 아키텍처 용어 8가지

| 용어 | 뜻 (요약) | 이 하네스에서 | 시각 |
|---|---|---|---|
| ① 아키텍처 드라이버 | 구조를 정하게 만드는 요구. 판별 질문: **"구조를 바꾸지 않고 수용할 수 있는가?"** — 그렇다면 드라이버가 아니다 | 라우팅 트리의 뿌리(`types.md` 4장) · B3·B5·B7의 드라이버 단계 · 요구 분류표(기능/품질 속성/제약 · 드라이버 O/X) | 02:54 · 03:33 |
| ② 품질 속성 | "얼마나 잘 되나". 기능(된다/안 된다)과 달리 **측정 가능한 숫자**로 적어야 요구사항이 된다(예: 피크 시 응답 95%가 1초 이내) | 판별 트리의 "얼마나를 숫자로?" → B7 · 드라이버 칸의 숫자, 없으면 "협의 필요" · 품질 속성 시나리오 6칸(자극원·자극·환경·대상·응답·측정) | 04:30 · 05:27 |
| 제약 사항 | 바꿀 수 없는 조건(기존 DB, 클라우드, 연동 시스템) | 드라이버 단계의 제약 칸 · 대안의 제외 조건 | 01:20 |
| ③ 택틱 | 품질 속성을 위한 전략 — **무엇을** 할지. 아직 "어떻게"는 없음(예: 성능을 위해 캐시를 둔다) | 대안 단계의 첫 열 · W²HO의 What | 06:19 |
| ④ 스타일 | 시스템 전체 구조의 큰 모양(레이어드, 이벤트 기반, 마이크로서비스 등) | 대안 단계 · 지금 구조를 말할 때(분석 파이프라인 = 이벤트 기반 + 서버리스 워커) | 06:59 |
| ⑤ 패턴 | 택틱을 **어떤 구조로** 구현할지, 검증된 해법(예: Cache-Aside) | 대안 단계의 둘째 열 · 구현 계획 · PR "무엇을 바꿨나" · W²HO의 How | 07:41 |
| 택틱·패턴의 구분 | 택틱 = 무엇을, 패턴 = 어떤 구조로, 트레이드오프 = 무엇을 치르나 — **층을 나눠** 말한다 | 모든 문서의 규칙 "무엇과 어떻게를 다른 칸에" | 08:32 |
| ⑥ 트레이드오프 | 한 품질 속성을 얻으면 다른 것을 잃는다. 대안마다 얻는 것·치르는 것을 함께 본다 | 비교표(열 = 드라이버의 품질 속성 전부, `++ / + / 0 / − / −−`, "아무것도 안 함" 포함) · **모든 PR의 `### 판단` 칸** | 09:21 |
| ⑦ 아키텍처 결정 | 트레이드오프를 보고 **우리 상황에 맞는** 전략을 고르는 것 | 결정 문장: "우리 상황에서는 X를 고른다. A를 얻고, B는 감수하며, C로 완화한다" | 10:17 |
| ⑧ ADR | 결정을 이유·대안·결과와 함께 남긴 기록. 나중에 "왜 이렇게 했지?"에 답한다 | `adr/NNNN-*.md` 또는 계획 파일의 "결정 기록" · 되돌리기 비용이 높으면 필수(ADR △) · 채택된 ADR은 고치지 않고 새 ADR로 대체 | 11:15 |
| 사고 흐름 | 비즈니스 목표 → 드라이버 → 대안(택틱·스타일·패턴) → 트레이드오프 → 결정 → ADR. **한 방향만이 아니다** — 가다가 드라이버로 돌아간다 | B5·B7 단계 순서 그대로 · "갈아타기"(`types.md` 5장) | 11:33 |
| 모호한 비즈니스 언어 | 고객 말("빠르게", "안 죽게")은 설계 언어로 옮기고, 숫자가 없으면 다시 묻는다 | 구체화(Phase 1) · 드라이버 단계의 "원문 → 설계 언어" | 12:37 |
| AI에게 시킬 때 | 드라이버·품질 속성·제약·허용 택틱·제외 조건을 넣어 시켜야 결과가 정확하다 | 구현(Phase 6)은 계획 문서의 결정·제외 조건 안에서만 | 01:20 |

## B. W²HO — 말하고 쓰는 순서

| 단계 | 뜻 (요약) | 이 하네스에서 | 시각 |
|---|---|---|---|
| **Why** | 왜 문제인가 — 배경, 지금의 고통, **수치·사례**. 공감이 먼저 생겨야 뒤를 받아들인다 | 구체화 · 이슈 "Issue Description" · 모든 단계 칸의 첫 줄 · 문서 맨 위 한 줄 | 04:24 |
| **What** | 그래서 무엇이 필요한가 — 해결책의 **개념**만, 방법은 아직 | 이슈 체크박스 · 택틱 · 결정 | 06:01 |
| **How** | 어떻게 구현하나 — 기술·도구·실행 방법 | 패턴 · 구현 계획 · PR "무엇을 바꿨나" | 06:35 |
| **Opinion** | 그래서 내 판단은 — 결론, 권고, 트레이드오프, 향후 방향, 교훈. **How에서 끝나면 보고서에 그친다** | PR `### 판단` · ADR 결과 · 단계 확정 때 3줄 요약의 마지막 줄 · improvements 회고 | 07:01 |
| 청중별 깊이 | 결정하는 사람에겐 Why·What·Opinion 중심(How는 요약), 실무 리더에겐 How를 깊게, 짧은 자리에선 Why → What → Opinion | 유형별 문서 무게(B1 커밋 한 줄 ~ B7 폴더) · 설명 자료(Phase 8)는 결정자용 | 08:50 · 10:00 |
| 기술 문서 순서 | 결정의 맥락(왜) → 결정(무엇) → 구현과 결론 | ADR 칸 순서 | 12:26 |
| 자가 점검 | Why로 시작하나? 수치·사례가 있나? What과 How를 나눴나? 청중에 맞췄나? Opinion으로 끝나나? | 단계 확정 전 점검 · `.claude/spec/issue-pr-writing.md` 자가 점검 | 12:41 |

## C. 이 하네스가 더한 말 (강의에 없음)

| 말 | 뜻 |
|---|---|
| 유형 (B1~B7·S1·S2) | 드라이버 판별 질문을 "어느 길로 갈까"로 넓힌 것 — 강의 흐름을 일의 무게만큼만 탄다 |
| 무게 질문 셋 | 되돌리기 비용 · 영향 범위 · 불확실성, 가장 높은 것이 무게 |
| 태그 | +스키마 · +계약 · +레포 간 · +제거 · +운영 — 단계와 ADR △를 더한다 |
| 기준선 (지금 재기) | 대안 전에 지금 상태를 재는 것. 리팩터링 = 동작 고정 테스트, 버그 = 실패하는 재현 테스트, 성능 = 숫자 |
| 관문 | 단계·작업이 끝났다고 말할 수 있는 조건 |
| 적합도 함수 | 기준선과 같은 방법(스크립트·테스트)으로 다시 재서 결정이 지켜지는지 보는 것 |
| 갈아타기 | 하다가 무게가 바뀌면 유형을 올리는 것 — 강의의 "한 방향이 아니다" |
| 오늘 일기 | 여러 날 이어지는 B5·B7에서 그날의 목표·순서만 따로 적는 파일 |
