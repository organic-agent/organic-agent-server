# 작업 유형 — 라우팅 규칙

> 2026-10-08 합의. 근거는 강의 두 편(아키텍처 용어 8가지 · W²HO — 용어 뜻은 [glossary.md](glossary.md))과 이 저장소 커밋 #153~#269.
> 강의 흐름(요구 → 드라이버 → 대안 → 트레이드오프 → 결정 → ADR)을 모든 일에 태우지 않는다. 유형이 어느 칸을 쓸지 정한다.

## 1. 무게 질문 셋 — 흐름의 무게는 "틀렸을 때 얼마나 비싼가"

| 질문 | 낮음 | 중간 | 높음 |
|---|---|---|---|
| 되돌리기 비용 | 코드만 되돌림 | 설정·배포를 되돌림 | 스키마·데이터 삭제·API 계약·다른 레포가 얽힘 |
| 영향 범위 | 파일 몇 개 | 도메인 하나 | 여러 도메인·여러 레포 |
| 불확실성 | 규칙대로 하면 답이 하나 | 대안이 여럿 | 숫자를 재 봐야 안다 |

- 셋 중 가장 높은 것이 무게다.
- 불확실성 "재 봐야 안다" → 기준선 측정 필수(B7) 또는 실험 먼저(S2).
- 되돌리기 비용 "높음" → ADR 필수(짧게라도).

## 2. 유형

| 코드 | 유형 | 신호 | 예 |
|---|---|---|---|
| B1 | 간단한 수정 | 한두 파일, 동작의 뜻이 안 바뀜 | 링크·문구, 변수명, nullable 필드 하나, 설정 값 하나, 스크립트 인자 |
| B2 | 간단한 기능 추가 | 있는 도메인 안에서 API·로직 하나, 기존 패턴 그대로 | 폴더 이름 변경 API(#260), 쿠폰 링크 목적지 조회(#262), 조회·수정 로직 추가 |
| B3 | 복잡한 기능 추가 | 새 도메인 폴더 또는 여러 도메인이 함께 바뀜, 새 테이블·새 권한 규칙 | 회차 보정 요청 + PDF(#264), 요금제·쿠폰(#207), 게스트 링크(#248), 폴더 합치기·되돌리기(#243·#247) |
| B4 | 리팩터링 — 국소 | 동작 그대로, 이름·위치·중복 정리, 한 도메인 | 포트 위치·DTO 접미사(#177), 폴더 이동 로직 분리(#200) |
| B5 | 리팩터링 — 구조 | 동작 그대로, 흐름·책임 나누기가 바뀜, 여러 클래스·도메인 | 분석 흐름 Step 분리(#201), category → folder 이동(#193) |
| B6 | 버그 수정 | 의도와 다르게 동작, 원인이 코드 안 | 하객 좋아요(#255), 목표일(#246), 재물질화 결과(#219) |
| B7 | 성능·용량 개선 | "느리다·못 버틴다"를 숫자로, 인프라까지 닿을 수 있음 | 업로드 → AI 폴더 시간, 동시 N명, 대량 갤러리 물질화(#160), GPU 전환 |
| S1 | 장애 대응 | 운영이 멈췄거나 사용자가 막힘 | 관리자 컨텍스트 500(#229), GPU 워커 디스크 부족 |
| S2 | 실험·스파이크 | 답을 모르고 재 봐야 안다, 산출물이 결과 문서 | GPU 벤치마크, 보정 요청 정제 평가, 부하 사전 측정 |

의존성 업그레이드·문서만·테스트만은 B1로 본다(동작이 바뀌면 그 유형으로).

## 3. 태그 — 무게를 올리는 것

| 태그 | 신호 | 더하는 규칙 |
|---|---|---|
| +스키마 | Flyway 마이그레이션이 있다 | `.claude/rules/migration.md` · 넓히기 → 좁히기 두 단계로 나눌지 · 되돌리는 방법 · ADR △ |
| +계약 | 웹이 보는 요청·응답이 바뀐다 | 바꾸기 전에 요청·응답 예시를 웹과 맞춘다 · 추가는 바로, 삭제·이름 변경은 두 단계 · PR에 "웹 영향" · ADR △ |
| +레포 간 | AI·infra·web 레포가 같이 바뀐다 | 배포 순서 표(PR 맨 위 경고) · 옛 버전과 한동안 같이 돈다 · ADR △ |
| +제거 | 기능·API·테이블을 없앤다 | 쓰는 곳 0 근거(로그·웹 검색·grep) · 데이터 백업 · 코드 먼저, 스키마는 다음 · ADR △ |
| +운영 | 인프라·배포·운영 설정·비용이 바뀐다 | dev에서 먼저(develop 흐름) · 되돌리는 방법 · 비용 변화 한 줄 |

ADR △ = 유형이 ADR을 안 쓰더라도 **되돌리기 어려운 그 결정만** 짧게 남긴다.

## 4. 30초 판별 트리

```
운영이 멈췄나? ── 예: S1
동작이 바뀌나?
 ├─ 아니오 ─ 한 도메인 안, 흐름 그대로? ─ 예: B4 / 아니오: B5
 └─ 예 ─ 원래 의도와 다르게 돌던 것? ─ 예: B6
         └─ 아니오 ─ "얼마나"를 숫자로 말해야? ─ 예: B7
                     └─ 아니오 ─ 새 도메인·여러 도메인·새 테이블? ─ 예: B3
                                 └─ 아니오 ─ 파일 한두 개, 뜻 그대로? ─ 예: B1 / 아니오: B2
답을 모르고 재 봐야 안다 → S2 먼저, 결론이 나면 그 결론으로 다시 판별
그다음 태그: +스키마 · +계약 · +레포 간 · +제거 · +운영
애매하면 무거운 쪽으로 — 첫 단계만 해 보고 내려올 수 있다
```

## 5. 갈아타기 — 하다가 무게가 바뀔 때

| 하던 것 | 신호 | 갈아탈 곳 |
|---|---|---|
| B1 | 동작의 뜻이 바뀜 · 테이블이 바뀜 | B2 (+스키마) |
| B2 | 새 테이블·새 도메인 · 다른 도메인 코드를 고쳐야 함 | B3 |
| B2·B3 | "얼마나 빨라야 하나"가 나옴 | 그 부분만 B7 |
| B4 | 응답 모양·스키마가 바뀜 | B2·B3 (+계약·+스키마) |
| B4 | 흐름 자체를 바꿔야 함 | B5 |
| B6 | 원인이 구조(동시성·설계)라 국소 수정으로 안 막힘 | 급한 부분은 B6, 근본은 B5·B7 이슈 |
| S1 | 같은 장애가 두 번 | 회고 + B5·B7 |
| S2 | 결론이 "바꾸자" | B3·B5·B7 (실험 결과가 기준선) |

## 6. 유형 → 커밋 타입·라벨·브랜치 (`.claude/spec/git-convention.md`)

| 유형 | 커밋 타입 |
|---|---|
| B1 | 일의 성격대로 (`fix`·`chore`·`docs`·`test`) |
| B2·B3 | `feat` |
| B4·B5 | `refactor` |
| B6 | `fix` |
| B7 | 사용자가 보는 동작이 바뀌면 `feat`, 아니면 `refactor` · CI·배포만이면 `cicd` |
| S1 | `hotfix` (main에서 분기) |
| S2 | `chore` (측정 스크립트) 또는 `docs` (결과 문서만) |

이슈 본문 맨 아래에 `작업 유형: <코드> <태그…>` 한 줄을 남긴다 — 나중에 유형별로 모으거나(B1 묶기) 회고할 때 검색한다.
