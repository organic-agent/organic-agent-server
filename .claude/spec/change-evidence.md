# 기존 코드 변경 근거 규칙

## 목적

기존 코드와 동작을 바꾸는 판단은 작성자에 대한 인상이나 선호가 아니라, 추적 가능한 계약과
재현 가능한 관찰에 근거해야 한다. 이 규칙은 코드 작성자가 누구인지와 관계없이 동일하게 적용한다.

근거의 목적은 "누가 잘못했는지"를 찾는 것이 아니라 다음 질문에 답하는 것이다.

- 현재 동작은 무엇이며 어떤 입력에서 확인되는가?
- 기대 동작은 무엇이고 어디에서 합의되었는가?
- 왜 이 범위의 변경이 필요하고, 더 작은 변경으로는 해결할 수 없는가?
- 변경 후 무엇으로 안전성을 확인했는가?

## 적용 범위

추적 중인 기존 파일의 구현을 수정하면 이 규칙을 적용한다. 다음 중 하나라도 달라지면
**기존 동작 변경**으로 본다.

- API 요청·응답, 상태 코드, 오류 코드 또는 예외 처리
- 도메인 규칙, 권한, 보안, 동시성, 멱등성 또는 데이터 의미
- 스키마, 마이그레이션, 외부 연동 또는 설정 기본값
- 다른 코드가 의존하는 내부 계약이나 작업 흐름

리팩터링처럼 동작을 보존한다고 주장하는 변경도 수정 목적, 동작이 같다는 판단 근거, 최소 범위와
회귀 검증을 남긴다. 동작 보존을 설명할 수 없으면 기존 동작 변경으로 분류한다.

기존 계약을 바꾸지 않고 새 경로·기능만 추가하는 작업에는 결함 재현을 억지로 요구하지 않는다.
대신 승인된 요구사항 또는 결정 출처, 현재 없던 기능과 새로 제공할 결과, 기존 코드와 맞닿는 범위,
비목표와 검증을 기록한다. 추가 작업이 기존 입력의 결과나 계약을 바꾸면 그 부분은 기존 동작 변경으로
분류해 아래의 전체 근거를 적용한다. 기존 파일을 전혀 수정하지 않는 순수 신규 산출물은 저장소의 일반
이슈·검증 절차를 따르며, 이 규칙 때문에 별도의 Actual vs Expected를 만들 필요가 없다.

## 기존 동작 변경에 필요한 근거

다음 항목을 구현 전에 GitHub 이슈에 기록한다. 각 항목은 리뷰어가 같은 결론을 재현할 수 있을 만큼
구체적이어야 하며, `해당 없음`이나 추측만으로 채우지 않는다.

1. **원 계약 또는 결정 출처**
   - 요구사항, 명세, API 계약, 테스트, 마이그레이션, GitHub 이슈·PR·commit 중 기대 동작을 뒷받침하는 링크나 경로를 남긴다.
   - 기존 결정 기록이 없다면 그 사실만으로 변경을 진행하지 않는다. 기대 동작을 결정할 권한이 있는 사람의 명시적 합의를 이슈에 먼저 남긴다.
2. **재현 가능한 Actual vs Expected**
   - 전제 조건, 입력 데이터, 요청 또는 실행 명령을 적고 현재 결과(Actual)와 기대 결과(Expected)를 분리한다.
   - 정책 변경이라면 현재 계약과 승인된 새 계약을 같은 형식으로 비교한다.
3. **영향 범위**
   - 영향받는 API, 호출자, 데이터, 배포·호환성 위험과 영향받지 않는 경계를 적는다.
4. **검토한 대안**
   - 유지, 설정 변경, 호출부 수정 등 현실적인 대안과 채택하지 않은 이유를 적는다.
5. **최소 변경과 비목표**
   - 문제를 해결하는 가장 작은 변경 범위와 이번 작업에서 의도적으로 바꾸지 않을 항목을 적는다.
6. **검증**
   - 이슈에는 검증 계획과 완료 기준을, PR에는 실제 실행한 명령·입력과 결과를 남긴다.
   - 실행하지 못한 검증은 누락하지 말고 사유, 남는 위험, 대체 확인 방법을 적는다.

현재 코드가 기대 동작과 다르다는 주장만으로는 부족하다. **Expected는 반드시 계약 또는 이슈에 기록된
명시적 결정과 연결**되어야 한다.

## 기록 위치와 연결

- 이슈는 구현 전 근거와 범위의 기준 문서다. 구현 중 근거나 범위가 달라지면 코드를 더 바꾸기 전에 이슈를 갱신한다.
- 작업 브랜치와 commit은 이슈 번호로 이 근거에 연결한다.
- PR은 이슈의 근거를 검토 가능한 수준으로 요약하고, 실제 diff가 최소 범위 및 비목표와 일치하는지 설명한다.
- PR의 검증 섹션에는 실제 명령과 결과를 적는다. `테스트 통과`처럼 재현할 수 없는 요약만 쓰지 않는다.
- 코드 주석은 복잡한 불변식을 설명할 수 있지만, 이슈와 PR의 변경 근거를 대신하지 않는다.

## Git 기록 사용 원칙

`git log`, `git show`, `git blame`은 현재 코드가 도입된 commit과 연결된 이슈·PR·결정 출처를 찾는
도구다. 다음은 변경 근거가 아니다.

- 특정 사람이 작성했다는 사실
- 코드가 오래되었거나 여러 사람이 수정했다는 사실
- 작성자의 의도, 역량 또는 실수를 추측한 평가
- 단순히 다른 스타일이 더 익숙하거나 깔끔하다는 선호

이력에서 얻은 정보를 근거로 쓸 때는 사람 이름 대신 관련 commit·이슈·PR과 그 안의 결정 내용을
인용한다. 작성자 평가는 이슈, commit, PR에 남기지 않는다.

## 중단 조건

기존 동작 변경에서 다음 중 하나라도 해당하면 구현, 스테이징, commit, push 또는 PR 생성을 중단하고
부족한 근거를 이슈에서 먼저 보완한다.

- Expected를 뒷받침하는 계약이나 명시적 결정이 없다.
- Actual과 Expected를 같은 조건에서 비교할 재현 절차가 없다.
- 영향 범위, 대안, 최소 변경 또는 비목표가 비어 있다.

모든 기존 코드 수정은 다음에 해당하면 같은 방식으로 중단한다.

- diff가 이슈에 기록된 범위를 벗어난다.
- 검증 결과가 없고, 미실행 사유와 대체 확인 및 남는 위험도 기록되지 않았다.

예를 들어 `blame상 다른 사람이 작성한 오래된 코드라 정리한다`는 근거가 아니다. 반면
`API 계약 commit과 달리 같은 요청이 500을 반환하며, 재현 요청·영향 API·대안·최소 수정·회귀
테스트가 이슈에 기록되어 있다`면 검토 가능한 변경 근거가 된다.
